# 系统化调试

## 概述

随机修复浪费时间并引入新 Bug。快速修补会掩盖根本问题。

**核心原则：** 在尝试修复之前，务必先找到根本原因。症状修复就是失败。

**违反本流程的字面要求就是违反调试的精神。**

## 铁律

```
未先调查根本原因，不得进行任何修复
```

如果你尚未完成第一阶段，你不能提出修复方案。

## 何时使用

适用于任何技术问题：
- 测试失败
- 生产环境中的 Bug
- 意外行为
- 性能问题
- 构建失败
- 集成问题

**特别要在以下情况下使用：**
- 时间紧迫（紧急情况让人倾向于猜测）
- "只快速修复一下"看起来很诱人
- 你已经尝试了多次修复
- 之前的修复没有生效
- 你没有完全理解该问题

**以下情况不要跳过：**
- 问题看似简单（简单的 Bug 也有根本原因）
- 你很匆忙（匆忙保证返工）
- 经理要求立即修复（系统化比瞎忙活更快）

## 四个阶段

你必须在进入下一阶段之前完成每个阶段。

### 第一阶段：根本原因调查

**在尝试任何修复之前：**

1. **仔细阅读错误消息**
   - 不要跳过错误或警告
   - 它们通常包含确切的解决方案
   - 完整阅读堆栈跟踪
   - 注意行号、文件路径、错误代码

2. **稳定重现**
   - 你能可靠地触发它吗？
   - 确切的步骤是什么？
   - 每次都会发生吗？
   - 如果无法重现 → 收集更多数据，不要猜测

3. **检查最近的更改**
   - 什么变化可能导致此问题？
   - Git diff、最近的提交
   - 新的依赖项、配置更改
   - 环境差异

4. **在多组件系统中收集证据**

   **当系统有多个组件时（CI → 构建 → 签名，API → 服务 → 数据库）：**

   **在提出修复方案之前，添加诊断检测手段：**
   ```
   对于每个组件边界：
     - 记录进入组件的数据
     - 记录离开组件的数据
     - 验证环境/配置的传播
     - 检查每层的状态

   运行一次以收集证据，显示它在哪一层断裂
   然后分析证据以识别出故障组件
   然后调查该特定组件
   ```

   **示例（多层系统）：**
   ```bash
   # 第1层：工作流
   echo "=== Secrets available in workflow: ==="
   echo "IDENTITY: ${IDENTITY:+SET}${IDENTITY:-UNSET}"

   # 第2层：构建脚本
   echo "=== Env vars in build script: ==="
   env | grep IDENTITY || echo "IDENTITY not in environment"

   # 第3层：签名脚本
   echo "=== Keychain state: ==="
   security list-keychains
   security find-identity -v

   # 第4层：实际签名
   codesign --sign "$IDENTITY" --verbose=4 "$APP"
   ```

   **这揭示了：** 哪一层失败了（secrets → workflow ✓, workflow → build ✗）

5. **追踪数据流**

   **当错误在调用栈深处时：**

   请参阅本目录中的 `root-cause-tracing.md` 了解完整的反向追踪技术。

   **快速版本：**
   - 错误值从何处产生？
   - 谁用错误值调用了这里？
   - 一直向上追踪直到找到源头
   - 修复源头，而非症状

### 第二阶段：模式分析

**在修复之前找到模式：**

1. **找到工作示例**
   - 在同一代码库中找到类似的工作代码
   - 有什么能正常工作且与出问题的代码相似？

2. **对照参考实现**
   - 如果要实现某个模式，请完整阅读参考实现
   - 不要略读——阅读每一行
   - 在应用之前完全理解该模式

3. **识别差异**
   - 工作代码和出问题代码之间有什么不同？
   - 列出每一个差异，无论多么微小
   - 不要假设"那个不可能有关系"

4. **理解依赖关系**
   - 它需要哪些其他组件？
   - 需要哪些设置、配置、环境？
   - 它做了哪些假设？

### 第三阶段：假设与测试

**科学方法：**

1. **形成单一假设**
   - 清楚地陈述："我认为 X 是根本原因，因为 Y"
   - 把它写下来
   - 具体明确，不要含糊

2. **最小化测试**
   - 做出尽可能小的改动来测试假设
   - 一次只改变一个变量
   - 不要同时修复多个问题

3. **验证后再继续**
   - 生效了？是 → 进入第四阶段
   - 没生效？形成新的假设
   - 不要在之上叠加更多修复

4. **当你不确定时**
   - 说"我不理解 X"
   - 不要假装知道
   - 寻求帮助
   - 进一步研究

### 第四阶段：实施

**修复根本原因，而非症状：**

1. **创建失败的测试用例**
   - 尽可能简单的重现方式
   - 尽可能使用自动化测试
   - 如果没有测试框架则用一次性测试脚本
   - **必须**在修复之前拥有
   - 使用 `superpowers:test-driven-development` 技能来编写合适的失败测试

2. **实施单一修复**
   - 针对已识别的根本原因
   - 一次只做一个改动
   - 没有"顺便"改进
   - 没有捆绑式重构

3. **验证修复**
   - 测试现在通过了？
   - 没有其他测试被破坏？
   - 问题真的解决了？

4. **如果修复无效**
   - 停止
   - 计数：你已经尝试了多少次修复？
   - 如果 < 3：返回第一阶段，用新信息重新分析
   - **如果 ≥ 3：停止并质疑架构（下面的第5步）**
   - 未经架构讨论，不要尝试第4次修复

5. **如果 3+ 次修复失败：质疑架构**

   **表明架构问题的模式：**
   - 每次修复都在不同地方揭示新的共享状态/耦合/问题
   - 修复需要"大规模重构"才能实施
   - 每次修复都会在其他地方产生新症状

   **停下来质疑基本问题：**
   - 这个模式从根本上说是合理的吗？
   - 我们是不是"纯粹因为惯性而在硬撑"？
   - 是否应该重构架构，而不是继续修复症状？

   **在尝试更多修复之前与你的人类伙伴讨论**

   这不是假设失败——这是架构错误。

## 红旗警示——停下来遵循流程

如果你发现自己有这样的想法：
- "先快速修复，之后再调查"
- "先试试改 X 看看行不行"
- "一次性做多个改动，然后跑测试"
- "跳过测试，我手动验证"
- "大概是 X 的问题，让我修一下"
- "我没有完全理解，但这可能行得通"
- "模式说用 X，但我会用不同的方式适配"
- "以下是主要问题：[列出修复方案而没有调查]"
- 在追踪数据流之前就提出解决方案
- **"再试一次修复"（已经尝试了 2+ 次）**
- **每次修复都在不同地方揭示新问题**

**以上任何一条都意味着：停下来。返回第一阶段。**

**如果 3+ 次修复失败：** 质疑架构（参见第四阶段第5步）

## 你的人类伙伴发现你做错时的信号

**注意这些重定向信号：**
- "那个没有发生吗？"——你未经验证就做出了假设
- "它能给我们展示……？"——你应该添加证据收集
- "别猜了"——你在没有理解的情况下提出修复方案
- "深度思考一下"——质疑根本问题，而不仅仅是症状
- "我们卡住了？"（沮丧）——你的方法不起作用

**当你看到这些时：** 停下来。返回第一阶段。

## 常见借口

| 借口 | 现实 |
|--------|---------|
| "问题很简单，不需要流程" | 简单的问题也有根本原因。流程对简单 Bug 来说也很快。 |
| "紧急情况，没时间走流程" | 系统化调试比猜了又试、试了又猜更快。 |
| "先试这个，之后再调查" | 第一次修复就定下了模式。从一开始就做对。 |
| "确认修复有效后再写测试" | 未经测试的修复不牢靠。先测试才能证明它。 |
| "一次修多个问题节省时间" | 无法隔离哪个有效。还会引入新 Bug。 |
| "参考太长了，我会调整模式" | 部分理解保证产生 Bug。完整阅读它。 |
| "我看到问题了，让我修" | 看到症状 ≠ 理解根本原因。 |
| "再试一次修复"（2+ 次失败后） | 3+ 次失败 = 架构问题。质疑模式，不要继续修。 |

## 快速参考

| 阶段 | 关键活动 | 成功标准 |
|-------|---------------|------------------|
| **1. 根本原因** | 读取错误、重现、检查变更、收集证据 | 理解什么出了问题以及为什么 |
| **2. 模式** | 找到工作示例、比较 | 识别差异 |
| **3. 假设** | 形成理论、最小化测试 | 确认或形成新假设 |
| **4. 实施** | 创建测试、修复、验证 | Bug 已解决，测试通过 |

## 当流程揭示"没有根本原因"

如果系统化调查揭示问题确实是环境相关的、时间依赖的或外部的：

1. 你已经完成了流程
2. 记录你调查了什么
3. 实施适当的处理措施（重试、超时、错误消息）
4. 添加监控/日志以便将来调查

**但是：** 95% 的"没有根本原因"的情况都是调查不完整。

## 辅助技术

这些技术是系统化调试的一部分，可在本目录中找到：

- **`root-cause-tracing.md`** - 通过调用栈反向追踪 Bug 以找到原始触发点
- **`defense-in-depth.md`** - 在找到根本原因后在多个层添加验证
- **`condition-based-waiting.md`** - 用条件轮询替代任意超时

**相关技能：**
- **superpowers:test-driven-development** - 用于创建失败的测试用例（第四阶段，第1步）
- **superpowers:verification-before-completion** - 在声称修复成功之前验证修复是否生效

## 实际效果

来自调试会话的数据：
- 系统化方法：15-30 分钟修复
- 随机修复方法：2-3 小时瞎忙活
- 首次修复成功率：95% 对比 40%
- 引入的新 Bug：接近于零 对比 常见
