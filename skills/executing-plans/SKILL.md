# 计划执行（Native 内联）

**自己在当前会话逐任务实现计划：不派实现者子代理，不派任务级审查员。全部任务完成后，派一个全新上下文的审查员审整个分支。**

**为什么内联：** SDD 每任务都要付一个全新实现者的成本——而「从零读代码库」是单项最贵的动作。内联只付「一个会话语境 + 末尾一个审查员」。它放弃的是每任务的 fresh context 和每任务的一双眼睛，用别的手段补回来：**本任务章节就是 spec，checkbox 就是记忆，TDD 是每任务的门控，末尾审查员是那双眼睛。**

**核心原则：** 计划已经做完了思考。照它执行，用「亲眼看它失败再通过」的测试证明每一步，留下能扛住你自己遗忘的记录。

## 前置条件

计划已被用户确认，且用户在执行交接时选了内联。

**无子代理工具时同样适用**——绝不伪造派发，就地执行。与 SDD 的分工判据见 `../subagent-driven-development/SKILL.md` 的「何时使用」。

## Setup

**隔离工作区：** 用 `superpowers:using-git-worktrees` 创建或校验工作区。**未经用户明确同意，绝不在 main/master 分支上开始实现。**

**读计划与 Spec：** 通读一遍计划建立索引，之后每任务只读自己那一段（不重读整份）。计划点名了 Spec 就也读它，它是计划据以论证的权威。

**强制加载 TDD：** 第 1 个任务之前加载 `superpowers:test-driven-development`。

**开工前记录 Base SHA：** `git rev-parse HEAD` 记下当前提交——末尾审查的 BASE 就是它（绝不是 `HEAD~1`）。

## 连续执行

任务之间**不停下来问「要继续吗」**。用户选内联是为了少花钱，不是为了每任务回答一次。「冲突 / 歧义 / 计划缺陷」一律现场裁决并继续——**裁决，不是停顿**。

**可以停的只有四件事：**

1. 不可逆或破坏性操作
2. 安全敏感动作
3. worktree 之外的副作用（merge、push 共享分支、发布）
4. 计划烂到每条前路都是猜

**中断恢复（上下文压缩 / 会话重开后）：** 已 `- [x]` 的任务不重做，从首个未勾的任务续跑。续跑前先 `git status` + `git log --oneline -5` 查半成品——上一会话可能在任务中途断掉，留下未提交改动或半截 commit。发现半成品：续用或回滚，记一条 Ruling，再继续。**信计划文件与 git log，不信会话记忆。**

## 每任务循环

### 1. 取任务

```
grep -n "^### Task N:" <计划文件>
```

**计划若含代码围栏，先确认命中行不在围栏内**——任务正文里出现 `### Task N:` 字样（示例代码、模板片段）时，裸 `grep` 会算出错误窗口，照着错窗口干活是**静默错任务**，无任何报错。

以该行号为起点、下一个 `### Task` 行为终点，Read 这一段。**不读整个计划。**

**每个任务都要重读自己的那一段**，包括你记得的——记忆是摘要，原文才有精确的值、签名、测试用例。

取段前先扫计划头部 `## Rulings` 区里涉及本任务 Consumes/文件的历史裁决——Rulings 区不在任何任务窗口内，不主动扫就看不到；相关裁决是本任务的约束（尤其在你没参与的前一段会话压缩之后）。

### 2. 按步骤做

计划的步骤已是 RED→GREEN 顺序，按原顺序在 `superpowers:test-driven-development` 下执行。**测试步骤的代码先写、先跑。亲眼看它失败是步骤本身，不是形式**——实现还不存在测试就通过，那是对测试本身的发现。

每个跑命令的步骤都有 `Expected:` 行。跑，读输出，比对。三种结果：

- **一致** → 下一步
- **代码错了** → 用 `superpowers:systematic-debugging` 找根因；绝不为了让输出对上就补症状
- **计划错了**（步骤与 spec 矛盾、上个任务的接口对不上、命令根本跑不通）→ 取满足 spec 的最小改动，按 Rulings 格式记进计划文件的 `## Rulings` 区，继续。**裁决要被携带，不是被记住**——下个任务取段时会扫 Rulings 区（见上文「取任务」），读到它

提交按计划的提交步骤来。跨多个 commit 没问题；审查的 BASE 是开工前记录的那个，**绝不是 `HEAD~1`**。

### 3. 完成契约

写 checkbox 之前，以下每条都要有**本会话的证据**——不是「diff 看着对」的推断：

- 本任务章节点名的每个测试都存在，且在本任务跑过，你读过输出
- 本任务最后一次测试运行通过——**跑的是项目测试命令，不是单个文件**
- 本任务章节里每条 `Expected:` 都跟真实输出比对过
- 每条偏离计划都有对应 Ruling

**缺任何一条，任务就没完成。** 这套证据的管辖技能是 `superpowers:verification-before-completion`——声称任务或整单完成之前，先加载它。

### 4. 收尾

1. **在本任务章节内追加一行证据**（紧接该任务的 checkbox 之后）：
   `> 证据：<测试命令> → <结果>`
   checkbox 是**裸布尔，装不下命令与结果**。EP 是内联执行、不派行号指针，所以在计划文件里增行是安全的（「只翻 checkbox 不增删行」是 SDD 的约束——SDD 靠行号指针定位任务）。这一行是上下文被压缩后唯一能证明「跑过什么」的东西。
2. Edit 计划文件：`- [ ]` → `- [x]`
3. `TaskUpdate({ taskId, status: "completed" })`

**Edit 必须在 TaskUpdate 之前。** 文件持久化优先于会话标记。

## 末尾审查门控

**全部任务 checkbox 全 `- [x]` 后**，进入与 SDD 相同的审查门控：

- 需求侧 `spec-review` **必跑**（模板 `../subagent-driven-development/spec-reviewer-prompt.md`）
- 质量侧 `code-review` **仅当交付物含可执行代码时跑**，且只审代码部分

**code-reviewer 用最强模型；spec-reviewer 按标准档**（与 SDD 分档一致）。内联执行省掉了每任务一份 fresh context，末尾的审查员就是那双眼——模型档位别省，也别用自己读一遍 diff 代替。

**无子代理工具时（Codex / Copilot / Gemini）：** 门控不能派子代理，但**不得因此跳过**。自己按 `../requesting-code-review/code-reviewer.md` 的检查项审一遍（**只读**，不改工作树、不移动 HEAD），并在最终报告写明「**最终审查：自审（无子代理工具）**」——**作者自审弱于全新审查员**，由用户决定是否够格合并。**绝不伪造派发。**

BASE 用 `git merge-base origin/main HEAD`。

- ❌ → 自己修（**你就是这里的实现者**），**一次修完全部 finding**；每个修复由 TDD 验证（写出复现 finding 的测试，看它失败，修到通过，再跑全量套件）。**修完不重跑审查**，理由见下方「不派二次审查」
- ✅ → `superpowers:finishing-a-development-branch`

**不派二次审查。** 修复已有覆盖测试回答「修好了吗」，套件运行回答「弄坏别的了吗」——再派一轮只会重读一遍。

## 收尾：Rulings 汇总

最终消息里列出，**穷尽**：

1. **我做的裁决**——每条含「错了代价是什么」
2. **延后的 Minor**——审查员标 Minor 的项，不进修复流程。**但先按效果重新定级**：审查员的标签评的是 **spec 的沉默**，不是用户实际拿到什么——**按用户实际拿到什么重判一遍**，够格的升进修复流程
3. **搁置判定**——code-reviewer「Declined to judge」清单里的每条，给出你的裁决（接受/不接受 + 理由）。模板向审查员承诺过「搁置的东西不会被静默丢弃」——这个清单就是兑现承诺的地方

这是用户唯一能看见「你替他做了哪些决定、放过了哪些 finding」的地方。

## 红线

- 别伪造派发——无子代理工具就自己干，别说「已派子代理」
- 别任务之间停下来请示
- 别跳过整体 spec-review
- 别拿单文件测试绿了当任务完成——跑项目测试命令
- 别用自己读一遍 diff 代替末尾审查——那比 fresh 审查员弱得多
- 别偏离计划而不记 Ruling
- 别创建 ledger / `progress.md`——计划 checkbox 就是进度真相源
- 别每任务重读整份计划——Setup 通读一次建立索引即可，之后只重读当前任务那一段
