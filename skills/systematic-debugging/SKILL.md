# 系统化调试

## 概述

随机修复浪费时间，还会制造新 bug。快速打补丁只是掩盖底层问题。

**核心原则：** 尝试修复之前，永远先找到根因。治标即失败。

**违反本流程的字面规则，就是违反调试的精神。**

## 铁律

```
没有先做根因调查，就没有修复
```

没完成 Phase 1，就不能提出修复。

## 何时使用

用于任何技术问题：
- 测试失败
- 生产环境 bug
- 意外行为
- 性能问题
- 构建失败
- 集成问题

**尤其在以下情况使用：**
- 时间压力下（紧急状况让猜测变得诱人）
- "就一个快速修复"看起来显而易见时
- 你已经试过多个修复时
- 上一个修复没起作用时
- 你还没完全理解问题时

**以下情况不要跳过：**
- 问题看起来简单（简单 bug 也有根因）
- 你在赶时间（赶工必然返工）
- 经理要求立刻修好（系统化比乱撞更快）

## 四个阶段

必须完成每个阶段才能进入下一个。

### Phase 1: 根因调查

**尝试任何修复之前：**

1. **仔细阅读错误消息**
   - 不要跳过错误或警告
   - 它们常常包含确切的解决方案
   - 完整阅读堆栈跟踪
   - 记下行号、文件路径、错误码

2. **稳定复现**
   - 能可靠地触发它吗？
   - 确切的步骤是什么？
   - 每次都发生吗？
   - 无法复现 → 收集更多数据，不要猜

3. **检查近期改动**
   - 有什么改动可能导致这个问题？
   - Git diff、近期 commit
   - 新依赖、配置变更
   - 环境差异

4. **在多组件系统中收集证据**

   **当系统有多个组件时（CI → build → signing、API → service → database）：**

   **提出修复之前，先加诊断埋点：**
   ```
   对每个组件边界：
     - 记录进入组件的数据
     - 记录离开组件的数据
     - 验证环境/配置的正确传递
     - 检查每一层的状态

   跑一次收集证据，看它在哪里断掉
   然后分析证据，定位出错的组件
   再调查那个具体组件
   ```

   **示例（多层系统）：**
   ```bash
   # 第 1 层：Workflow
   echo "=== Secrets available in workflow: ==="
   echo "IDENTITY: ${IDENTITY:+SET}${IDENTITY:-UNSET}"

   # 第 2 层：Build script
   echo "=== Env vars in build script: ==="
   env | grep IDENTITY || echo "IDENTITY not in environment"

   # 第 3 层：Signing script
   echo "=== Keychain state: ==="
   security list-keychains
   security find-identity -v

   # 第 4 层：Actual signing
   codesign --sign "$IDENTITY" --verbose=4 "$APP"
   ```

   **这揭示了：** 哪一层失败（secrets → workflow ✓、workflow → build ✗）

5. **追踪数据流**

   **当错误深藏在调用栈中时：**

   完整回溯技术见本目录的 `root-cause-tracing.md`。

   **快速版：**
   - 坏值从哪来？
   - 是谁用坏值调用了它？
   - 持续向上追踪，直到找到源头
   - 在源头修复，不要修症状

### Phase 2: 模式分析

**修复之前先找出模式：**

1. **找出可工作的示例**
   - 在同一代码库中定位相似的、能正常工作的代码
   - 有什么正常工作的、与坏掉的部分相似？

2. **对照参考实现**
   - 若在实现某个模式，完整阅读参考实现
   - 不要略读 —— 每一行都要读
   - 应用之前先完整理解该模式

3. **找出差异**
   - 正常工作的和坏掉的之间有什么不同？
   - 列出每一处差异，无论多小
   - 不要假定"那个不可能有关系"

4. **理解依赖关系**
   - 它还需要哪些其他组件？
   - 需要哪些设置、配置、环境？
   - 它做了哪些假设？

### Phase 3: 假设与验证

**科学方法：**

1. **提出单一假设**
   - 清晰陈述："我认为 X 是根因，因为 Y"
   - 写下来
   - 要具体，不要含糊

2. **最小化验证**
   - 做尽可能最小的改动来验证假设
   - 一次一个变量
   - 不要同时修多个东西

3. **继续之前先验证**
   - 起作用了吗？是 → Phase 4
   - 没起作用？提出新假设
   - 不要在原有基础上叠加更多修复

4. **当你不知道时**
   - 说"我不理解 X"
   - 不要假装知道
   - 求助
   - 做更多研究

### Phase 4: 实施

**修根因，不修症状：**

1. **创建失败测试用例**
   - 最简单的复现
   - 可能的话用自动化测试
   - 没有框架就用一次性测试脚本
   - 修复前必须有
   - 用 `superpowers:test-driven-development` 技能编写规范的失败测试

2. **实施单一修复**
   - 针对已识别的根因
   - 一次一个改动
   - 不要"既然来了顺手改"的改进
   - 不要夹带重构

3. **验证修复**
   - 测试现在通过了吗？
   - 没有破坏其他测试？
   - 问题真的解决了吗？
   - **在声称成功之前使用 `superpowers:verification-before-completion` 技能**

4. **如果修复不起作用**
   - 停
   - 数一数：你已经试过几个修复了？
   - 若 < 3：回到 Phase 1，带着新信息重新分析
   - **若 ≥ 3：停下，质疑架构（见下面第 5 步）**
   - 不要在架构讨论之前尝试第 4 个修复

5. **3+ 个修复失败后：质疑架构**

   **表明架构有问题的模式：**
   - 每个修复都在不同地方暴露出新的共享状态/耦合/问题
   - 修复需要"大规模重构"才能实现
   - 每个修复都在别处制造新症状

   **停下，质疑根本前提：**
   - 这个模式根本上站得住脚吗？
   - 我们是不是"纯靠惯性在硬撑"？
   - 应该重构架构，还是继续修症状？

   **在尝试更多修复之前，先和你的用户伙伴讨论**

   这不是一个失败的假设 —— 这是一个错误的架构。

## 红旗 —— 停下并遵循流程

如果你发现自己在想：
- "先快速修一下，回头再调查"
- "就改改 X 看看管不管用"
- "一次改多个，跑测试"
- "跳过测试，我手动验证"
- "大概是 X，我来修那个"
- "我没完全理解，但这个也许能用"
- "模式说要用 X，但我改成别的"
- "主要问题有：[不调查就列出一堆修复]"
- 在追踪数据流之前就提修复方案
- **"再试最后一个修复"（试过 2+ 次之后）**
- **每个修复都在不同地方暴露新问题**

**以上全部意味着：停下。回到 Phase 1。**

**若 3+ 个修复失败：** 质疑架构（见 Phase 4.5）

## 你的用户伙伴暗示你做错了

**留意这些纠正信号：**
- "是不是根本没发生？" —— 你没验证就做了假设
- "它会展示给我们看吗……？" —— 你本应加入证据收集
- "别猜了" —— 你没理解就提修复
- "深入思考一下" —— 质疑根本前提，不只是症状
- "我们卡住了？"（沮丧）—— 你的方法不管用

**看到这些信号时：** 停下。回到 Phase 1。

## 常见合理化

| 借口 | 现实 |
|------|------|
| "问题很简单，不需要流程" | 简单问题也有根因。对简单 bug，流程很快。 |
| "紧急情况，没时间走流程" | 系统化调试比猜来猜去的乱撞更快。 |
| "先试试这个，然后再调查" | 第一个修复就定下了模式。从一开始就做对。 |
| "等确认修复起作用了再写测试" | 未经验证的修复不牢靠。测试先行才能证明它。 |
| "一次修多个更省时间" | 无法定位到哪个起了作用。还会引入新 bug。 |
| "参考实现太长，我自己改改模式" | 理解不完整必然出 bug。完整读完。 |
| "我看到问题了，让我来修" | 看到症状 ≠ 理解根因。 |
| "再试最后一个修复"（2+ 次失败后） | 3+ 次失败 = 架构问题。质疑模式，不要接着修。 |

## 快速参考

| 阶段 | 关键活动 | 成功标准 |
|-------|---------------|------------------|
| **1. 根因** | 读错误、复现、检查改动、收集证据 | 理解 WHAT 和 WHY |
| **2. 模式** | 找可工作示例、对比 | 找出差异 |
| **3. 假设** | 形成理论、最小化验证 | 确认或提出新假设 |
| **4. 实施** | 创建测试、修复、验证 | bug 解决、测试通过 |

## 当流程显示"没有根因"

如果系统化调查显示问题确实是环境性的、时序相关的或外部的：

1. 你已完成流程
2. 记录你调查了什么
3. 实施适当的处理（重试、超时、错误消息）
4. 加入监控/日志以便将来调查

**但是：** 95% 的"没有根因"案例是调查不完整。

## 支撑技术

这些技术是系统化调试的一部分，就在本目录中：

- **`root-cause-tracing.md`** —— 沿调用栈向后追踪 bug，找到最初的触发点
- **`defense-in-depth.md`** —— 找到根因后，在多层加入校验
- **`condition-based-waiting.md`** —— 用条件轮询替代任意超时

**相关技能：**
- **superpowers:test-driven-development** —— 用于创建失败测试用例（Phase 4 第 1 步）
