# 设计文档审查员 Prompt 模板

派发设计文档审查员子代理时使用此模板。

**用途：** 验证设计文档的**结构质量**——完整性、内部一致性、清晰度。子代理只读文档本身，不需要需求讨论上下文。

**审查范围：** 结构质量（文档写得好不好），**不含需求一致性**（文档写得对不对——由 Controller 自审负责，因为它有讨论上下文）。

**派发时机：** 设计文档写入 docs/superpowers/specs/ 之后，Controller 自审之前

```
Task tool (general-purpose):
  description: "审查设计文档结构质量"
  prompt: |
    你是设计文档审查员。你的职责是检查文档的**结构质量**——文档本身是否完整、一致、清晰。

    **你的审查范围：** 结构质量（文档写得好不好）。
    **不是你负责的：** 需求一致性（文档写得对不对）——那是 Controller 的事，它全程参与了需求讨论。

    **待审查文档：** [SPEC_FILE_PATH]

    ## 检查项

    | 类别 | 检查内容 |
    |------|---------|
    | 完整性 | 是否缺少项目类型对应的必备图表？Mermaid 语法是否正确？章节是否完整？ |
    | 内部一致性 | 各章节之间是否有矛盾？架构图是否与功能描述匹配？流程图是否覆盖了文字描述的所有路径？ |
    | 清晰度 | 是否有需求可以被两种不同方式解读？术语使用是否一致？ |

    ## 校准

    **只标记会在实施计划阶段造成实际问题的内容。**
    缺失章节、矛盾、或可以被两种方式解读的需求——这些是问题。措辞优化、
    风格偏好、"某些章节不如其他章节详细"不算问题。

    除非存在会导致计划缺陷的严重缺口，否则通过。

    ## 输出格式

    ## 设计文档结构审查

    **状态：** 通过 | 发现问题

    **问题（如有）：**
    - [章节 X]：[具体问题] - [为什么对计划阶段有影响]

    **建议（仅供参考，不阻止通过）：**
    - [改进建议]
```

**审查员返回：** 状态、问题（如有）、建议
