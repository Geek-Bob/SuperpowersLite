# 编写实施计划

## 概述

编写任务分解计划，将设计文档拆分为可独立执行、适合 TDD 的任务。每个任务应足够清晰，使子代理无需阅读其他任务即可实现。

**核心原则：** 计划定义构建什么和如何验证。子代理决定如何实现。不要在计划中写实现代码——写验收标准。假设子代理是熟练的开发者：他们需要清晰的任务边界、文件路径和测试期望，而不是用来抄的代码。

**开始时声明：** "我正在使用 writing-plans 技能创建实施计划。"

**上下文：** 若在隔离的 worktree 中工作，执行时通过 `superpowers:using-git-worktrees` 创建。

**计划保存到：** `docs/superpowers/plans/YYYY-MM-DD-<功能名称>.md`（用户偏好覆盖此默认值）。

## 范围检查

设计文档涵盖多个独立子系统时，它应该在头脑风暴阶段就被拆分为子项目设计文档。若没有，建议拆成单独的计划——每个子系统一个，每个计划独立产出可工作、可测试的软件。

## 文件结构

定义任务之前，先规划哪些文件会被创建或修改、每个文件的职责——这是拆分决策锁定的地方。

- 设计边界清晰、接口定义明确的单元，每个文件一个明确职责
- 代码量控制在一次能完整理解的范围内时，推理最准、编辑最可靠；优先小而专注的文件
- 一起变更的文件放在一起；按职责拆分，不按技术层拆分
- 已有代码库中遵循既有模式，不单方面重构；但正被修改的文件已臃肿时，在计划中包含拆分

此结构为任务分解提供依据。每个任务应产出独立的变更，且单独来看也是合理的。

## 任务粒度

**每个任务是一个独立可测试的单元（子代理 15-30 分钟）：** 产出可工作、已测试的模块/组件；有清晰的输入/输出和验收标准（`- [ ]` checkbox）；涉及不同文件时可并行执行。

**任务内的步骤是 TDD 工作流指引（纯有序列表，不用 checkbox）：** 编写失败测试 → 运行验证失败 → 实现使测试通过 → 运行验证通过 → 提交。**步骤写测试描述和验收标准，不写实现代码。**

**拆到「能独立测试 + 能独立通过验收」即止。** 每个任务 = 一次子代理派发 = 数十 k 基础开销：拆成 10 个任务，启动成本是 5 个的两倍，而实现内容可能只占单次总量的 15-30%。两个任务强耦合到无法分别验收时，合并比硬拆更省。

## 计划文档头部

**每个计划必须以以下头部开始：**

```markdown
# [功能名称] 实施计划

> **给执行代理的说明：** 逐任务实现此计划。执行方式（SDD 子代理派发 / Native 内联执行）由用户在执行交接时二选一。步骤使用 checkbox（`- [ ]`）语法进行跟踪。

**目标：** [一句话描述构建什么]

**架构：** [2-3 句话描述方案]

**技术栈：** [关键技术/库]

**Base SHA：** `[开工前记录的 SHA]`

**Spec：** `[设计文档路径]`（冲突裁决的绑定依据——SDD / Native 在 setup 时读取）

## Rulings

---

## Global Constraints

[逐字精确值——子代理照抄，不解释、不推断：版本号、路径约定、命名前缀、禁改文件清单、CLI 精确语法、行尾约定等。]

## 文件结构映射

| 文件 | 职责 | 归属任务 |
|------|------|---------|
| `exact/path/to/file.ts` | [该文件做什么、边界在哪] | Task N |

## Review Focus

[5 类最易咬人的输入 / 失效模式——spec 暗示过、但没有任何任务的测试覆盖到的那些，每类标注归属任务。**每条都要在归属任务里补一个钉住它的测试**，写进该任务自己的步骤。]

1. [输入或失效模式] → Task N
2. [输入或失效模式] → Task N
3. [输入或失效模式] → Task N
4. [输入或失效模式] → Task N
5. [输入或失效模式] → Task N

```

**Rulings 区格式：** 每条裁决一行，三个字段用 ` — `（em dash 前后各一空格）分隔：

> **Ruling:** <决定了什么> — <为什么> — <错了代价是什么>

- **空区即无裁决：** 无裁决时保留空区，不写「无」——避免误以为需要逐条填写，也污染 diff。
- **禁止引入：** 完整 Ledger、progress.md、逐任务历史记录、决策之外的流水账。计划文件的 checkbox 追踪状态，Rulings 只记录裁决。
- **可变面授权：** SDD 执行时只翻 checkbox 不增删行；executing-plans 执行时每任务章节内追加一行「证据」——两者是计划文件可变面的全部例外。
- **收尾汇总：** 执行完成后，最终报告必须汇总所有 Rulings 供用户复核。

**三节要点：** Global Constraints 是**逐字精确值**，子代理按字面执行、不作同义改写，控制器派发时随指针（路径 + `offset`/`limit`）一并传递；文件结构映射是「改哪些文件、各职责、归属哪个任务」一览；Review Focus 的**载荷机制是「测试钉住」**——每条由归属任务的测试钉住，而不是只让末尾审查员多看几眼（官方 eval 里每个实现者都在「spec 暗示过、却从未点名」的输入上崩，只有测试能拦住它，审查员的注意力拦不住）。

## 任务结构

````markdown
### Task N: [组件名称]

**目标：** [一句话——此任务交付什么]

**设计文档索引：** `docs/superpowers/specs/<名称>-design.md#<标题锚点>` — spec-reviewer 对照原始规格验证

> **必须是精确的章节锚点，不是整个文件。** 标题 `### Agent 管理` → `#agent-管理`；`## 核心功能` → `#核心功能`；`### listAgents()` → `#listagents`。
> 错误示例：`spec.md`（整个文件）、`spec.md#`（空锚点）、`spec.md#<章节>`（占位符）。正确示例：`spec.md#核心功能`、`spec.md#agent-管理`。
> 设计文档索引仅传递给 spec-reviewer，不给实现者。

**需求描述：**
[3-5 句话——模块职责、输入/输出、关键行为、约束条件。让子代理理解它要构建什么]

**产出（Produces）：**
- 文件：`exact/path/to/file.ts` — 本任务创建或修改的文件路径
- 模块：`XxxService` — 本任务产出的可被其他任务引用的模块/类/组件
- 类型：`IXxx`（如有新定义）— 本任务新定义的类型或接口

**消费（Consumes）：**
- Task 0：`IUser`、`Result<T>` (@`src/types/domain.ts`) — Domain 类型（契约定义）
- Task 0：`IUserService` (@`src/services/user-service.ts`) — 接口签名（本任务实现它）
- Task 0：`IUserRepository` (@`src/repos/user.ts`) — 接口签名（注入使用）

> **Produces/Consumes 用于自动构建依赖图和计算执行分层。** 每个 Consumes 引用必须是精确的 Task 编号，引用不存在的 Task → 计划不合法。
> **`(@路径)` 是给下游子代理的指路牌：** 消费该契约时直接 Read 该文件，不必全库 `Grep` 找定义。路径取自该 Task 的 `Produces`（文件），同一文件的多个接口可合并一行。

**文件：**
- 创建：`exact/path/to/file.ts`
- 修改：`exact/path/to/existing.ts`
- 测试：`exact/path/to/file.test.ts`

**验收标准：**
- [ ] 函数 `createConversation()` 插入记录并返回 id
- [ ] 函数 `listConversations()` 返回所有对话，按 updated_at DESC 排序
- [ ] 所有测试通过：`npx vitest run src/path/to/file.test.ts`

**步骤：**
1. 编写测试（遵循 TDD 技能：Red → Green → Refactor）
2. 运行测试，验证失败
3. 实现使测试通过
4. 运行测试，验证通过
5. 提交
````

> **验收标准 vs 步骤：** 验收标准用 `- [ ]` checkbox，是任务交付物的质量契约——spec-reviewer 对照它验证，控制器按它标记完成。步骤用纯有序列表，是实现者的 TDD 工作流程指引，不需要外部跟踪。

## 任务的合格形态

每个任务必须是这个形状——**缺任何一项即计划失败**：

- **需求描述**：具体、非空。不是「添加适当的错误处理」/「添加校验」/「处理边界情况」这类无标准语句，不是「TBD / TODO / 稍后实现 / 补充细节」，不是只有一句话
- **验收标准**：`- [ ]` checkbox 逐条可验证，spec-reviewer 对照它验证
- **Produces** 非空；**Consumes** 引用存在的 Task 编号且附 `(@路径)`——路径缺失会让下游子代理退化为全库 `Grep` 找定义
- **模块职责** + Produces/Consumes 声明齐全；引用的类型、函数、方法都在某个任务中定义
- **Spec Reference**：精确章节锚点（如 `#契约与接口`），不是占位符（`#<章节>`）也不是只指向整个文件（`spec.md` 无锚点）

**可省略：** 实现代码、具体测试用例——子代理通过 TDD 技能自行编写测试。

## 执行分层

写完所有任务后，根据 Produces/Consumes 自动分析依赖关系，构建执行分层表。分层决定 subagent-driven-development 的执行顺序：同层并行、跨层串行。

### 分层算法

```
1. 收集所有任务的 Produces 和 Consumes
2. 构建依赖图：
   - Task B 的 Consumes 引用 Task A 的 Produces 中的模块/类型 → 建立边 A → B
   - Task A 和 Task B 的 Produces.文件 有交集 → 后声明的依赖先声明的
3. 检测循环依赖：图中有环 → 计划不合法，修复后重新分层
4. 拓扑排序 → 自然分层：
   - Layer 0 = 入度为 0 的任务
   - Layer 1 = 去掉 Layer 0 后入度为 0 的任务
   - ...重复直到所有任务分配完毕
```

### 分层表格式

```markdown
## 执行分层

> 由 Produces/Consumes 自动分析得出。同层任务修改不同文件且无依赖关系 → 可并行执行。

| 层级 | 任务 | 依赖 | 可并行 |
|:----:|------|------|:------:|
| L0 | Task 0: 契约定义 | 无 | — |
| L1 | Task 1: UserRepository | Task 0 | ✅ |
| L1 | Task 2: OrderRepository | Task 0 | ✅ |
| L2 | Task 4: UserService | Task 0,1 | ✅ |
| L3 | Task 8: DI + 路由 + 集成 | Task 6,7 | — |
```

**分层原则：** 层数不由规则决定，由依赖关系自然涌现（不预设 3 层或 5 层）；契约任务（定义共享类型/接口）永远是 Layer 0；同层任务必须**修改不同文件 + Consumes 无相互引用**才是安全并行；两个任务修改同一文件时算法自动排到不同层。

## 计划审查

派**计划文档审查员**子代理审查完整计划，模板 [plan-document-reviewer-prompt.md](plan-document-reviewer-prompt.md)（输入：计划路径 + 设计文档路径）。

**就地修复报告里的全部问题。无需重新审阅——修完继续，然后交给用户确认。**

> **为什么计划侧派子代理、spec 侧自己审：** 计划有客观结构面（依赖图环、文件冲突、Task 编号引用、Produces/Consumes 非空），外部审查员拿计划 + spec 两份材料能独立验，且作者写长计划时容易漏依赖；spec 的需求一致性则只有全程在场者能验。

## 用户确认门控（强制阻断）

审查修复完后，**你必须停下来等待用户确认**才能进入执行阶段：

1. 向用户呈现完整计划
2. 明确询问："请审阅这份实施计划。任务拆分是否合理？验收标准是否完整？是否需要调整？"
3. **在用户明确确认计划之前，禁止进入执行阶段**
4. 如果用户要求修改 → 修改计划 → 再次呈现 → 等待确认，重复直到用户明确确认

这是强制阻断。在用户确认计划已批准之前，你不能调用 subagent-driven-development。

## 执行交接

计划保存并审查后，把路径给用户。**用户明确确认计划之后**，在两种执行方式间二选一——若用户此前已指定执行方式，沿用即可，不再问。

**用户尚未指定时：**

> 计划已完成并保存到 `docs/superpowers/plans/<文件名>.md`。请审阅。选哪种执行方式？
>
> - **子代理（Subagent-driven）**——每个任务派一个全新子代理实现，末尾一次整体审查。上下文最干净；代价是每任务一次子代理启动（固定开销数十 k token）+ 从零读代码库。
> - **内联（Native）**——本会话亲自逐任务实现，末尾派一个全新审查员（**用最强模型**）审整个分支。**最省最快**；代价是中途没有独立审查。计划本身承载了设计，中档模型即可胜任。
>
> **这份计划我建议 <二选一>，因为 <一句话取自计划本身：要不要每任务审查门、计划有多长、出错上线的代价多大>。**

**推荐判据：**

| 计划特征 | 推荐 |
|---------|------|
| 要每任务审查门；或计划长到后续任务会在压缩后的上下文里跑 | 子代理 |
| 任务基本独立、不需每任务审查；计划够细 | 内联 |
| 任务数少（≤3–4）或计划本身不长 | 内联——派发次数少，省下的启动开销大于隔离收益 |

**两者前提相同——任务基本独立。** 紧耦合时两条路都不适用：该手工执行，或回去重新 brainstorming。

**用户选定后：** 选子代理 → **必须**使用 `superpowers:subagent-driven-development`；选内联 → **必须**使用 `superpowers:executing-plans`。
