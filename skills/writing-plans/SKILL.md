# 编写实施计划

## 概述

编写任务分解计划，将设计文档拆分为可独立执行、适合 TDD 的任务。每个任务应足够清晰，使子代理无需阅读其他任务即可实现。

**核心原则：** 计划定义构建什么和如何验证。子代理决定如何实现。不要在计划中写实现代码——写验收标准。

假设子代理是熟练的开发者。他们需要清晰的任务边界、文件路径和测试期望——而不是用来抄的代码。

**开始时声明：** "我正在使用 writing-plans 技能创建实施计划。"

**上下文：** 如果在隔离的 worktree 中工作，应在执行时通过 `superpowers:using-git-worktrees` 技能创建。

**计划保存到：** `docs/superpowers/plans/YYYY-MM-DD-<功能名称>.md`
- （用户偏好的计划位置会覆盖此默认值）

## 范围检查

如果设计文档涵盖多个独立子系统，它应该在头脑风暴阶段就被拆分为子项目设计文档。如果没有，建议将其拆分为单独的计划——每个子系统一个。每个计划应独立产出可工作、可测试的软件。

## 文件结构

在定义任务之前，先规划哪些文件将被创建或修改，以及每个文件的职责。这是拆分决策锁定的地方。

- 设计边界清晰、接口定义明确的单元。每个文件应有一个明确的职责。
- 当代码量控制在一次能完整理解的范围内时，你的推理最准确，编辑也最可靠。优先使用小而专注的文件，而非承担过多的文件。
- 一起变更的文件应该放在一起。按职责拆分，而非按技术层拆分。
- 在已有代码库中，遵循既有的模式。如果代码库使用大文件，不要单方面重构——但如果你正在修改的文件已经变得臃肿，在计划中包含拆分是合理的。

此结构为任务分解提供依据。每个任务应产出独立的变更，且单独来看也是合理的。

## 任务粒度

**每个任务是一个独立可测试的单元（子代理 15-30 分钟）：**
- 任务产出可工作、已测试的模块/组件
- 任务有清晰的输入/输出和验收标准（用 `- [ ]` checkbox）
- 如果任务涉及不同文件，可以并行执行

**任务内的步骤是 TDD 工作流指引（纯有序列表，不用 checkbox）：**
- "为 X 行为编写失败的测试"——步骤
- "运行测试，验证失败"——步骤
- "实现 X 使测试通过"——步骤
- "运行测试，验证通过"——步骤
- "提交"——步骤

**禁止：** 在步骤中写实现代码。写测试描述和验收标准。

## 计划文档头部

**每个计划必须以以下头部开始：**

```markdown
# [功能名称] 实施计划

> **给执行代理的说明：** 必须使用子技能：使用 superpowers:subagent-driven-development 逐任务实现此计划。步骤使用 checkbox（`- [ ]`）语法进行跟踪。

**目标：** [一句话描述构建什么]

**架构：** [2-3 句话描述方案]

**技术栈：** [关键技术/库]

---
```

## 任务结构

````markdown
### Task N: [组件名称]

**目标：** [一句话——此任务交付什么]

**设计文档索引：** `docs/superpowers/specs/<名称>-design.md#<标题锚点>` — spec-reviewer 对照原始规格验证

> **必须是精确的章节锚点，不是整个文件。** 从设计文档中复制对应章节的标题，转换为 anchor 格式：
> - 标题 `### Agent 管理` → `#agent-管理`
> - 标题 `## 核心功能` → `#核心功能`
> - 标题 `### listAgents()` → `#listagents`
>
> **错误示例：** `spec.md`（整个文件）、`spec.md#`（空锚点）、`spec.md#<章节>`（占位符）
> **正确示例：** `spec.md#核心功能`、`spec.md#agent-管理`、`spec.md#切换机制`
>
> 设计文档索引仅传递给 spec-reviewer，不给实现者。

**需求描述：**
[3-5 句话——模块职责、输入/输出、关键行为、约束条件。让子代理理解它要构建什么]

**产出（Produces）：**
- 文件：`exact/path/to/file.ts` — 本任务创建或修改的文件路径
- 模块：`XxxService` — 本任务产出的可被其他任务引用的模块/类/组件
- 类型：`IXxx`（如有新定义）— 本任务新定义的类型或接口

**消费（Consumes）：**
- Task 0：`IUser`、`Result<T>` — Domain 类型（契约定义）
- Task 0：`IUserService` — 接口签名（本任务实现它）
- Task 0：`IUserRepository` — 接口签名（注入使用）

> **Produces/Consumes 用于自动构建依赖图和计算执行分层。** 每个 Consumes 引用必须是精确的 Task 编号。引用不存在的 Task → 计划不合法。声明了 Consumes 但实际没用到 → 审查员会发现。

**文件：**
- 创建：`exact/path/to/file.ts`
- 修改：`exact/path/to/existing.ts`
- 测试：`exact/path/to/file.test.ts`

**验收标准：**
- [ ] 函数 `createConversation()` 插入记录并返回 id
- [ ] 函数 `listConversations()` 返回所有对话，按 updated_at DESC 排序
- [ ] 删除对话级联删除消息
- [ ] 所有测试通过：`npx vitest run src/path/to/file.test.ts`

**步骤：**
1. 编写测试（遵循 TDD 技能：Red → Green → Refactor）
2. 运行测试，验证失败
3. 实现使测试通过
4. 运行测试，验证通过
5. 提交
````

> **验收标准 vs 步骤：** 验收标准用 `- [ ]` checkbox，是任务交付物的质量契约——spec-reviewer 对照它验证，控制器按它标记完成。步骤用纯有序列表，是实现者的 TDD 工作流程指引，不需要外部跟踪。

## 禁止占位符

每个任务必须有明确的需求描述和验收标准。以下是**计划失败**——永远不要写这些：
- "TBD"、"TODO"、"稍后实现"、"补充细节"
- "添加适当的错误处理" / "添加校验" / "处理边界情况"（没有具体标准）
- 需求描述为空或只有一句话
- Produces 或 Consumes 为空、或 Consumes 引用不存在的 Task 编号
- 没有模块职责和 Produces/Consumes 声明
- 引用未在任何任务中定义的类型、函数或方法
- 设计文档索引使用占位符（`#<章节>`）或只指向整个文件（`spec.md` 无锚点）

**可省略的内容：** 实现代码、具体测试用例。子代理通过 TDD 技能自行编写测试。

## 执行分层

写完所有任务后，根据 Produces/Consumes 自动分析依赖关系，构建执行分层表。分层决定了 subagent-driven-development 的执行顺序：同层并行、跨层串行。

### 分层算法

```
1. 收集所有任务的 Produces 和 Consumes
2. 构建依赖图：
   - Task B 的 Consumes 引用 Task A 的 Produces 中的模块/类型 → 建立边 A → B
   - Task A 和 Task B 的 Produces.文件 有交集 → 后声明的依赖先声明的
3. 检测循环依赖：图中有环 → 计划不合法，修复后重新分层
4. 拓扑排序 → 自然分层：
   - Layer 0 = 入度为 0 的任务
   - Layer 1 = 去掉 Layer 0 后入度为 0 的任务
   - ...重复直到所有任务分配完毕
```

### 分层表格式

```markdown
## 执行分层

> 由 Produces/Consumes 自动分析得出。同层任务修改不同文件且无依赖关系 → 可并行执行。

| 层级 | 任务 | 依赖 | 可并行 |
|:----:|------|------|:------:|
| L0 | Task 0: 契约定义 | 无 | — |
| L1 | Task 1: UserRepository | Task 0 | ✅ |
| L1 | Task 2: OrderRepository | Task 0 | ✅ |
| L1 | Task 3: Logger | Task 0 | ✅ |
| L2 | Task 4: UserService | Task 0,1 | ✅ |
| L2 | Task 5: OrderService | Task 0,2 | ✅ |
| L3 | Task 6: UserController | Task 4 | ✅ |
| L3 | Task 7: OrderController | Task 5 | ✅ |
| L4 | Task 8: DI + 路由 + 集成 | Task 6,7 | — |
```

### 分层原则

- **层数不由规则决定，由依赖关系自然涌现。** 不预设 3 层或 5 层——依赖结构说了算
- **契约任务（定义共享类型/接口）永远是 Layer 0。** 它不消费任何任务的产出
- **同层任务必须满足：** 修改不同文件 + Consumes 无相互引用 → 安全并行
- **文件冲突自动串行：** 两个任务修改同一文件 → 分层算法自动将它们排到不同层

### 典型分层模式

| 项目类型 | 典型层数 | 说明 |
|---------|:------:|------|
| 简单 CLI / 工具 | 1-2 层 | L0 契约 + L1 实现，无需集成层 |
| 单体后端 CRUD | 3-4 层 | L0 契约 → L1 数据层 → L2 业务层 → L3 集成 |
| 纯前端组件 | 2-3 层 | L0 类型 + Token → L1 组件并行 → L2 页面组装 |
| 前后端分离 | 4-7 层 | 前端和后端各有自己的依赖链，自然叠加 |

## 牢记

- 始终使用精确的文件路径
- 每个任务有清晰的需求描述、模块职责和验收标准（不写测试用例——那是 TDD 的事）
- 精确的命令及预期输出
- DRY、YAGNI、TDD、频繁提交
- 当任务涉及不同文件时，应可并行执行

## 保存与审查

计划提交后，立即派发独立子代理审查。使用 `skills/writing-plans/plan-document-reviewer-prompt.md` 模板构建 prompt。

子代理同时拥有计划文档和设计文档，能独立完成全部审查——**需求一致性 + 结构质量**，无需 Controller 再补审：

| 检查维度 | 检查内容 |
|---------|---------|
| 设计文档对齐 | 计划是否覆盖设计文档所有需求？有无遗漏或曲解？有无范围蔓延？ |
| 完整性 | TODO、占位符、不完整的任务、缺失步骤 |
| 任务拆分 | 任务边界清晰，步骤可执行 |
| 可构建性 | 工程师能否按此计划实施而不卡住？ |
| 一致性 | 任务之间使用的类型、方法签名和属性名是否匹配？ |

子代理发现问题 → 修复计划 → 重新提交 → 重新审查，直到通过。

## 用户确认门控（强制阻断）

子代理审查通过后，**你必须停下来等待用户确认**才能进入执行阶段：

1. 向用户呈现完整计划
2. 明确询问："请审阅这份实施计划。任务拆分是否合理？验收标准是否完整？是否需要调整？"
3. **在用户明确确认计划之前，禁止进入执行阶段**
4. 如果用户要求修改 → 修改计划 → 再次呈现 → 等待确认
5. 重复直到用户明确确认计划正确

这是强制阻断。在用户确认计划已批准之前，你不能调用 subagent-driven-development。

## 执行交接

仅在用户明确确认计划后 → 调用 `superpowers:subagent-driven-development` 执行它。
