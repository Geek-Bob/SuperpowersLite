# 完成前验证

## 概述

未经验证就声称工作完成，是不诚实，不是高效。

**核心原则：** 证据永远先于断言。

**违反这条规则的字面，就是违反它的精神。**

## 铁律

```
没有新鲜的验证证据，就不做完成声明
```

如果你在这条消息里没有运行过验证命令，就不能声称它通过。

## 门控函数

```
在声称任何状态或表达满意之前：

1. 明确: 哪条命令能证明这个声明？
2. 运行: 执行完整命令（新鲜、完整）
3. 阅读: 读完整输出，检查 exit code，清点失败数
4. 验证: 输出能确认这个声明吗？
   - 不能: 带着证据陈述实际状态
   - 能: 带着证据陈述声明
5. 只有到这一步: 才做出声明

跳过任何一步 = 说谎，而不是验证
```

## 常见失败

| 声明 | 需要什么 | 什么不算数 |
|-------|----------|----------------|
| 测试通过 | 测试命令输出：0 失败 | 上一次运行、"应该能通过" |
| Linter 干净 | Linter 输出：0 错误 | 部分检查、外推 |
| 构建成功 | 构建命令：exit 0 | Linter 通过、日志看着不错 |
| Bug 已修复 | 测试原始症状：通过 | 改了代码、假设已修复 |
| 回归测试有效 | 已验证 Red-green 循环 | 测试通过了一次 |
| 代理已完成 | VCS diff 显示有改动 | 代理报告"成功" |
| 需求已满足 | 逐行对照检查清单 | 测试通过 |

## 红旗 - 停下

- 使用"应该"、"大概"、"似乎"
- 在验证之前表达满意（"太好了！"、"完美！"、"完成！"等）
- 即将未经验证就 commit/push/PR
- 信任代理的成功报告
- 依赖部分验证
- 想着"就这一次"
- 累了，想让工作赶紧结束
- **任何暗示成功、却未曾运行验证的措辞**

## 反合理化

| 借口 | 现实 |
|--------|---------|
| "现在应该能工作了" | 运行验证 |
| "我有信心" | 信心 ≠ 证据 |
| "就这一次" | 没有例外 |
| "Linter 过了" | Linter ≠ 编译器 |
| "代理说成功了" | 独立验证 |
| "我累了" | 疲惫 ≠ 借口 |
| "部分检查就够了" | 部分什么也证明不了 |
| "换个说法，规则就不适用了" | 精神高于字面 |

## 关键模式

**测试：**
```
✅ [运行测试命令] [看到：34/34 通过] "所有测试通过"
❌ "现在应该能通过了" / "看着对"
```

**回归测试（TDD Red-Green）：**
```
✅ 写 → 运行（通过）→ 还原修复 → 运行（必须失败）→ 恢复 → 运行（通过）
❌ "我写了一个回归测试"（未经 red-green 验证）
```

**构建：**
```
✅ [运行构建] [看到：exit 0] "构建通过"
❌ "Linter 通过了"（linter 不检查编译）
```

**需求：**
```
✅ 重读计划 → 创建检查清单 → 逐项验证 → 报告缺口或完成
❌ "测试通过，阶段完成"
```

**代理委派：**
```
✅ 代理报告成功 → 检查 VCS diff → 验证改动 → 报告实际状态
❌ 信任代理报告
```

## 何时适用

**始终在以下之前：**
- 任何形式的成功/完成声明
- 任何满意的表达
- 任何关于工作状态的正面陈述
- commit、创建 PR、任务完成
- 移动到下一个任务
- 委派给代理

**规则适用于：**
- 精确措辞
- 转述与同义词
- 成功的暗示
- 任何暗示完成/正确的沟通
