# 子代理驱动开发

派子代理执行计划，逐层并行。所有任务完成后过审查门控——需求侧 `spec-review` 永远跑，质量侧 `code-review` 仅当交付物含可执行代码时跑。

## Setup

1. **计划已确认**——未确认？停止。
2. **隔离工作区**——用 `superpowers:using-git-worktrees` 创建或校验。**未经用户明确同意，绝不在 main/master 上开始实现。**
3. **读计划与 Spec**——通读计划，记下 Global Constraints，逐任务建 todo。计划点名了 Spec 就**也读它**：spec 是计划据以论证的权威，计划内部的冲突对照 spec 裁决，而不是对照计划文本自己。读不到 spec 就在最终报告里记一句，据之做出的裁决标为临时。
4. **记录 Base SHA**——`git rev-parse HEAD`，后续每任务派发的 BASE 都用它（禁令见「diff 获取协议」）。
5. **强制加载 TDD**——第 1 个任务之前加载 `superpowers:test-driven-development`。它管辖每个任务的每一步；计划里写着「先写失败测试」不构成豁免。

## 何时使用

```
有实施计划？
  ├─ 否 → 先 brainstorming，或手工执行
  └─ 是 → 任务间基本独立？
            ├─ 否（紧耦合）→ 手工执行，或先 brainstorming
            └─ 是 → 用户选了内联，或无子代理工具？
                      ├─ 是 → superpowers:executing-plans（Native）
                      └─ 否 → 本技能
```

SDD 与 Native **共享同一前提：任务基本独立**。紧耦合时两个前提同时失效——分层退化为串行，计划步骤也互相纠缠；此时用 SDD 只剩子代理成本，用 Native 只剩重新设计的风险，**该做的是手工执行或回头重新 brainstorming**。

**分界是「要不要每任务审查门」，或「计划是否长到后续任务会在压缩后的上下文里执行」**——不是耦合紧不紧。第三个判据是固定开销 × 任务数：每次派发都重付一份基础开销（system prompt + 工具定义 + 指令文件，量级数十 k token；命中 Prompt Caching 时约按 10% 计费，但不保证命中），任务少时该成本占比极高——3 个任务派 3 次 ≈ 付 3 份启动费，而 Native 只付 1 份。**只有任务多到「计划会被压缩」时，SDD 的上下文隔离收益才抵得过这笔启动费**（完整对比见 writing-plans 执行交接节）。

两者共用同一份工作区约定与审查门控，任务之间都不停顿。

## 执行

```
读取计划 → 提取「执行分层」表 → TaskCreate 所有任务
  → 阶段 1：逐层并行执行
  → 阶段 2：审查门控（spec-review 必跑，code-review 按交付物分流）
```

不间断执行所有任务。**只有四类事情能让你停下**（其余一律现场裁决并继续）：不可逆或破坏性操作、安全敏感动作、worktree 之外的副作用（merge、push 共享分支、发布）、计划烂到每条前路都是猜。终态——BLOCKED 无法解决、真正阻塞的歧义、全部完成——同样停下。

**这四类是自主执行的边界，不是可选项**——现场裁决（见 Rulings 三触发时机）不包括在无人同意的情况下 merge、push 共享分支或发布。

## 控制器角色：纯协调者

| ❌ 不做 | ✅ 做 |
|--------|------|
| 读代码、审查代码 | 只读报告 |
| 修代码 | 只决定下一步 |
| 跳过必跑的 spec-review | 只协调层级推进 |
| 信任实现者报告未验证 | 只在审查门控通过后标记完成 |

## 阶段 0：分层编排

控制器读取 writing-plans 已计算好的「执行分层」表，照表执行——**不重复分析依赖**。分层表异常？退回 writing-plans 重新生成。

## 指针化派发

派发**只给指针，不给正文**。控制器在派发 prompt 里只放五样东西：

| 组件 | 内容 |
|------|------|
| 路径 | 计划文件绝对路径 + 目标文件路径 |
| 定位 | `offset` / `limit`（行号窗口），或精确章节标题 |
| 额外约束 | 本任务独有的边界（Auth Scope、禁改文件清单、专用规则） |
| 相关 Ruling | `## Rulings` 区里涉及本任务 Consumes/文件的历史裁决（没有则省略）——Rulings 区在计划头部，**不在任务窗口内**，实现者自己看不到 |
| 报告路径 | `.superpowers/sdd/<plan-slug>/task-N-report.md` |

**禁止写进派发 prompt：** 任务全文粘贴、会话历史回放、前序任务摘要、整份计划正文。

**为什么：** 有真实会话的派发 prompt 达 42k 字符，其中 99% 是粘贴的历史。规则管不住粘贴惯性——用行号指针让正文物理上不进上下文，而不是靠模型自觉。

### 行号解析约定

派发前**现场解析**任务行号，**不硬编码**：

```
grep -n "^### Task N:" <计划文件>
```

以该行号为起点、下一个 `### Task` 行为终点，据此填 `offset` / `limit`。N 精确匹配——`^### Task 1:` 不会误匹配 `### Task 10:`。

**计划若含代码围栏，先确认命中行不在围栏内。** 任务正文里出现 `### Task N:` 字样（示例代码、模板片段）时，裸 `grep` 会算出错误窗口，实现者照着错窗口干活——**静默错任务**，无任何报错。

**防行号漂移：** 进度**只翻 checkbox（`- [ ]` → `- [x]`），不增删行**。新增或删除任何行都会让后续任务的 `offset` 失效，指针派发随之错位——这是「只翻 checkbox」的理由，不是格式洁癖。

### diff 获取协议（子代理自跑）

审查员与修复者**自跑 git diff**，控制器不代劳、不粘 diff：先 `git diff --stat BASE..HEAD` 看全景，再按文件 `git diff -- <path>` 分批精读（改动超 5 个文件时先看 stat 概览）。

**BASE 三禁令：**

- 必须是派发前记录的 SHA，**禁用 `HEAD~1`**——多 commit 任务会被静默丢弃前序 commit 的改动，审查员漏审
- 整体审查用 `git merge-base origin/main HEAD`，**禁用裸 `origin/main`**——分支点之后的 main 新文件会被显示成幻影删除
- 审查前先确认 `BASE` 是 `HEAD` 的祖先，且 `BASE..HEAD` 非空——否则实现者可能提交到了别的分支，审查员会对一个空 range 给出「干净」结论并放行。不满足即按 BLOCKED 上报

**禁止**控制器把 diff 正文粘进任何 prompt。

### 产出路径约定

所有产出固定在仓库根的 `.superpowers/sdd/<plan-slug>/` 下：`task-N-report.md`（实现者报告）、`review-N-report.md`（审查员报告）。**`plan-slug` 取法：** 计划文件名去扩展名（`docs/superpowers/plans/2026-09-23-foo.md` → `2026-09-23-foo`）。

**创建 `.superpowers/sdd/.gitignore`（内容一行 `*`）**，保证产出不进 `git status`、不被 `git add` 带走——技能是装到用户仓库里跑的，那里的 `.gitignore` 不受 Lite 控制。

**`git clean -fdx` 会连报告一起删。** 进度可凭计划 checkbox 从 git 恢复；报告不可恢复——但**审查不依赖它们**：spec-reviewer 自行读代码与 git diff 验证（输入不含报告路径，也不信任报告）。报告的价值是事后审计，缺失时照常派发审查。

### 子代理输出契约（实现者与审查员通用）

详细内容**落 report 文件**，返回控制器的**只有四项**：状态 / commit / 一行测试摘要 / 顾虑。**禁止**把报告全文、测试日志、diff 正文贴回控制器。

**无开场白：** 返回的每一行都必须携带信息——第一行直接给结论，每行 = 结论 / 带 `file:line` 的发现 / 跑过的检查。禁止"好的，我来分析一下"式开场白、过程叙述、"综上所述"式收尾——控制器只读报告，叙述与礼貌性总结对它是零信息、纯 token 浪费。

### 禁止 ledger / progress.md

**只创建 report 类文件。** 进度持久化的唯一真相源是计划文件 checkbox（见「进度持久化」）。**禁止** ledger、`progress.md`、逐任务历史记录——那是为应对上下文压缩的状态恢复机制，checkbox 已解决；再造一份只会制造第二个会不同步的真相源。

## 阶段 1：逐层并行执行

```
Layer 0 → 全部完成 → Layer 1（所有任务并行）→ 全部完成 → Layer 2 → ... → Layer N
```

**同层并行：** 所有任务同时派发，互不等待；各自独立走 `实现(TDD) → 自审 → 提交 → 标记完成`；任务失败只影响该任务（派新实现者修复），同层其他任务继续；同层最慢任务决定本层耗时。

**跨层串行：** 当前层所有任务完成后，才能进入下一层。

### 同层安全并行的前提

同层任务满足：修改不同文件 + Consumes 无相互引用 + 共享契约层类型——它们对着同一份接口写代码，互不干扰。

**git 暂存区与索引是共享资源。** 同层多个实现者在同一 worktree 各自 `git add` + `git commit`——并发暂存会把别人 add 了一半的文件裹进自己的 commit（污染审查 diff），撞 `index.lock` 只是报错，互染才是静默灾难。实现者提交纪律：**只 add 本任务文件，commit 用路径限定**（`git commit -m "<msg>" -- <本任务文件>`），撞锁等 2 秒重试（见 implementer-prompt.md）。官方对并行实现是整段禁止的；Lite 并行的代价由这两条纪律扛。

### 同形小任务合并派发

同层里若有**多个同类小改**（同一种一行修改、常量替换、加字段，反复出现在不同文件）——**别一任务一派**。合成**一份派发简报**，列出每个文件及其改动，整批发给一个子代理，把它的 diff 当整体审。把「一任务一派」留给需要独立判断、独立测试或独立审查面的工作。

**为什么：** 每次派发都要重付一份基础开销，同形小任务恰恰是最付不起这份开销的一类。

### 任务级：自审，不派审查员

任务级只有**自审**——实现者本人在同一份上下文里完成，零额外成本：

- **契约约束**：只能用 Consumes 里声明的接口和类型
- **强制 TDD**：Red→Green→Refactor，亲眼看它失败
- **四维自审**：完整性 / 质量 / 纪律 / 测试 → 有顾虑就报 `DONE_WITH_CONCERNS`

**自审 ≠ 审查。** 自审是作者视角、提交前的自查；实现者只看得到自己那一段 `offset/limit`，原理上查不了跨任务一致性——**这正是末尾审查门控存在的理由**。别读成「两道审查」：任务级一道自查（免费），全局一道他审（贵，但独立）。

### Per Task 流程

```
grep -n "^### Task N:" <计划文件> → 得该任务 offset/limit
派实现者（新子代理，只传计划文件路径 + offset/limit + Consumes 契约及其 `(@路径)` + 模块职责 + 相关 Ruling（有则附）+ 额外约束 + 报告路径）
  → 强制加载 TDD 技能，Red→Green→Refactor
  → 实现者四维自审（完整性/质量/纪律/测试）
  → 报告全文写入 task-N-report.md
  → 返回：状态 + commit + 一行测试摘要 + 顾虑（无开场白）
  → Edit 计划文件 checkbox [- → x] → TaskUpdate 标记完成
```

**详细 Prompt 模板：** `./implementer-prompt.md`

## 进度持久化（任务级强制）

任务实现+自审通过后，**立即**回写计划文件——不是会话结束批量更新。

1. **派发时建档：** `TaskCreate({ subject, description, activeForm })` → 得 taskId
2. **任务开始时：** `TaskUpdate({ taskId, status: "in_progress" })`
3. **完成后先 Edit 计划文件：** 找到该任务的 checkbox，将 `- [ ]` 改为 `- [x]`
4. **再 TaskUpdate 标记：** `TaskUpdate({ taskId, status: "completed" })`

**Edit 必须在 TaskUpdate 之前。** 文件持久化优先于会话标记。Edit 失败？重试，最多 3 次；仍失败？以 BLOCKED 状态暂停，向用户汇报。

理由：TaskUpdate 的状态只在当前会话有效，会话结束进度丢失；计划文件是唯一的持久化真相源，中断后重开能从 checkbox 状态恢复；实时回写确保任何时候看计划文件都知道进度。

### 中断恢复（上下文压缩 / 会话重开后）

已 `- [x]` 的任务**不重派**；从首个未勾的任务续跑。续跑前先 `git status` + `git log --oneline -5` 查半成品——上一会话可能在任务中途断掉，留下未提交改动或半截 commit。发现半成品：续用或回滚，记一条 Ruling，再派发。**信计划文件与 git log，不信会话记忆**——恢复所需的数据面（checkbox / commit）Lite 全有，缺的只是这条程序。

## 阶段 2：审查门控（按交付物分流）

**所有任务完成后**，进入审查门控。子代理看到完整需求地图和全部实现代码。

**分流规则：** 需求侧 `spec-review` **永远跑**；质量侧 `code-review` **仅当交付物含可执行代码时跑**，且**只审代码部分**。

```
整体 spec-review（需求覆盖度 + 任务间一致性）
  → ❌ → 派修复者 → 重新整体 spec-review（循环）
  → ✅
交付物含可执行代码？
  ├─ 否（纯文档 / 技能 Markdown）→ 跳过 code-review → finishing-a-development-branch
  └─ 是 → 整体 code-review（仅代码部分）
            → ❌ → 派修复者 → 重新整体 code-review（循环）
            → ✅ → finishing-a-development-branch
```

**spec-review 看"做了什么"，code-review 看"做得怎样"**——按交付物分流，不是「两道必跑关卡」。判据是**交付物内容**，不是任务标签。

### 为什么纯文档 / 技能任务跳过 code-review

**这条理由必须保留**——否则后人会把 code-review 重新加回来。

code-review 的检查项是**错误处理、类型安全、Schema 迁移、安全隐患**。这些对技能 Markdown 是**无效项**：Markdown 没有控制流、没有类型、没有运行时、没有 schema。硬跑它只会产出「命名不够好」这类噪音 finding，并诱使修复者为了通过审查去改写文档措辞——偏离需求，纯亏 token。

需求侧审查对文档**完全有效**：漏需求、需求曲解、范围蔓延、任务间接口不一致，在文档里同样成立。所以纯文档 / 技能任务：**spec-review 跑，code-review 跳**。

### 例外：交付物含可执行代码（防一刀切）

技能 / 文档任务里夹带可执行代码（技能中内嵌 bash / node / python 片段，或附带的脚本）时：

- **code-review 只审那些代码片段**——按代码标准查错误处理、类型安全、安全隐患
- **文档部分仍走 spec-review**——不因为文件是 `.md` 就免审

**禁止**因为「这个任务主要是写文档」就整单跳过 code-review——那会把夹带的可执行代码放过去。

### 派发审查员的禁令（防预判 + 只读）

**控制器不得预判 finding。** prompt 里出现"不要标记 X""X 不算缺陷""最多 Minor""这个计划就是这么选的"——停，你在替审查员做决定。真出现误报就**让它报出来，在审查循环里裁定**——隔着 prompt 猜，比审查员看着代码判断更容易错。

**审查员只读、不接受辩解。**

- 审查**不得改动工作树或分支**——审查员跑 `git checkout` 会让后续 commit 变成孤儿
- 实现者报告里的"我故意不抽象"、"这里留着是有原因的"**不能劝退审查员**——理由不构成证据，代码本身才是

**"无法从 diff 判定"是有效结论。** 需求落在未改动的代码里、或横跨多个任务时，审查员应标注「无法从 diff 判定」并**继续审其余部分**，不因此中断。这些条目由控制器逐条自行裁定——控制器持有计划与跨任务上下文，审查员没有；确认是真缺口的，按 spec ❌ 处理，进入修复流程。

### 整体 spec-review（需求侧：永远跑）

1. 控制器派发**整体 spec-reviewer 子代理**（新子代理），模板 `./spec-reviewer-prompt.md`
2. 提供：SPEC 路径 + Plan 路径（子代理自读任务清单）+ BASE SHA（子代理自跑 git diff）
3. 子代理**按需读取全量代码**，自主定位功能实现完成度
4. 检查：需求覆盖度 / 任务间一致性 / 范围蔓延 / 需求曲解
5. ❌ 不通过：派新实现者修复（附整体审查报告 + 指派"修复 Task X 的 Y 问题"）→ 重新派发整体 spec-reviewer（循环直到通过）
6. ✅ 通过：交付物含可执行代码 → 进入整体 code-review（仅代码部分）；否则 → 直接进入 finishing-a-development-branch

### 整体 code-review（质量侧：仅当交付物含可执行代码时）

1. 控制器调用 `Skill("superpowers:requesting-code-review")`
2. 按指引获取 BASE_SHA/HEAD_SHA，填 `code-reviewer.md` 模板，派发**整体 code-reviewer 子代理**（新子代理）
3. code-reviewer 看到**全量 diff**（BASE..HEAD）
4. 检查：架构 / 文件职责 / 可测试性 / 结构合规 / 测试质量 / 安全 / 性能
5. ❌ 不通过：派新实现者修复（附整体审查报告 + 指派"修复 Task X 的 Y 问题"）→ 重新调用 requesting-code-review（循环直到通过）
6. ✅ 通过：进入 finishing-a-development-branch

### 修复子代理授权（ONE fix dispatch）

**一次审查暴露的全部 finding 打包给同一个修复者，一次派一个**——不按 finding 逐个派发。派新实现者（**新子代理**），附带：

- **整体审查报告**（列明全部 finding）
- **被指派 Task 编号**（"修复 Task X 的 Y 问题"）
- **原始任务描述**

**为什么 ONE：** 每个 finding 单独派一个修复者 → N 倍子代理启动成本 + N 份全量代码上下文重复加载；同一文件的多个 finding 还会互相覆盖。修完**只重跑发现问题的那一侧审查**，不重跑另一侧。

**复审是限定范围的：** 记录修复前的 SHA 作为 `FIX_BASE`，把复审范围限定为 `FIX_BASE..HEAD` 并附上 finding 清单，让复审者核对**修复本身**，而不是把整个任务或整个分支重读一遍（EP 已这么做：「再派一轮只会重读一遍」，SDD 口径与之保持一致）。

### 循环上限与残余上呈

**整体审查循环最多 3 轮。** 到第 3 轮仍有 finding：停下，把**全部残余 finding 连同「为什么修不掉」**上呈用户，由用户决定继续、放宽标准、还是接受。**没有出口的循环会让会话卡在没人知道的地方。**

### Minor 分流与上呈

审查员标 Minor 的 finding **不进修复流程**（`code-reviewer.md` 的「严重/重要/次要」分级就是给这里用的）。**但先按效果重新定级**——审查员的标签评的是 **spec 的沉默**，不是用户实际拿到什么；按用户实际拿到什么重判一遍，够格的升进修复流程。

- 逐条记进最终报告的「延后的 Minor」清单，**穷尽列举**
- `finishing-a-development-branch` 呈现选项时把该清单交给用户，由用户判断哪些必须在合并前修

**无人读的汇总 = 静默丢弃。** 每条 Minor 要么被修、要么被显式延后并告知用户，没有第三种归宿。

## 处理实现者状态

| 状态 | 动作 |
|------|------|
| DONE | 标记完成（Edit checkbox → TaskUpdate）|
| DONE_WITH_CONCERNS | 读顾虑。正确性/范围问题 → 修复后再标记。观察性意见 → 记录，正常标记完成 |
| NEEDS_CONTEXT | 补充上下文，重新派发 |
| BLOCKED | 上下文不足 → 补充后重派。需更强推理 → 升级模型。任务太大 → 拆分。计划问题 → 升级给用户 |

**别忽略升级。别不改变就重试。卡住了就必须改变什么。**

## Rulings（裁决记录）

计划是静态的，执行是动态的。现场偏离计划文本做判断时，记一行 Rulings，让用户能复核判断对错。**格式契约由 writing-plans 计划模板定义**——本节只定义触发时机：

| 触发 | 记什么 |
|------|--------|
| 审查发现与计划文本冲突 | 冲突点 + 裁决（改计划 / 改实现）+ 理由 |
| 实现者 BLOCKED 且控制器现场改计划 | 原计划文本 + 改成什么 + 为什么 |
| 整体审查不通过且裁决某 finding 不成立 | finding + 判不成立的理由 |

**在飞保护：** 现场改计划会增删行，让**在飞子代理**的行号窗口错位——同层还有任务没返回时，把改计划推迟到层结束；等不及（阻塞的就是本层），改完立即把受影响任务按新行号重新派发。

**收尾时：** Rulings 汇总进最终报告，供用户复核判断对错。code-reviewer「Declined to judge」清单一并逐条裁决后汇总（接受/不接受 + 理由）——模板向审查员承诺过「搁置不会被静默丢弃」，控制器是兑现人。

## 模型选择

派发时**必须显式写明模型**——不写就继承你当前会话的模型（往往是最强最贵的那档），整套分档被静默击穿；派发 prompt 里模型字段永远显式。

- 机械任务（1-2 文件、清晰规格）→ 廉价（haiku）
- 集成任务（多文件、跨模块）→ 标准（sonnet）
- 设计/架构、整体 code-review（架构 / BUG 审查）→ 最强模型（opus）
- 整体 spec-review（需求覆盖度）→ 标准模型（sonnet）

**中档（sonnet）地板，不得降到廉价模型：审查员**（产出是「判断」，判断失准的代价是漏审，比审查费贵得多）**与「从散文描述实现」的实现者**（计划不含实现代码，要从验收契约反推实现，推理密度高于抄代码）。只有机械任务（改文档措辞、翻转 checkbox、按清单逐条核对）与小型修复 diff 的局部 re-review 才允许降到廉价模型。

**轮次比 token 单价更重要：** 最便宜的模型常常跑 2–3 倍轮次，总价反而更贵——看**完成任务的期望总成本（单价 × 轮次）**，不看单价。

**Prompt Caching：** 派发子代理时保持 prompt 前缀稳定——固定的系统提示、技能内容、模板骨架放前缀，随任务变化的内容放后缀；命中缓存的输入按 **10%** 计费，别为了「更漂亮」重排 prompt 结构。

## 禁止事项

- 控制器自己读代码、自己审查、自己修代码
- 跳过整体 spec-review（它永远必跑）
- 交付物含可执行代码却整单跳过整体 code-review
- 跳过层级（上层未完成就进入下层）／不同层任务并行派发／同层内串行
- 只在 TaskUpdate 标记完成但不回写计划文件 checkbox——Edit 必须先于 TaskUpdate
- 审查门控通过后，继续追加任务
- 创建 ledger / `progress.md` / 逐任务历史记录
- 把 diff 正文、报告全文、前序任务摘要、任务全文、会话历史、整份计划正文粘进主上下文或派发 prompt——让子代理自跑 `git diff`
- 让子代理读整个计划文件——只给它任务章节的 `offset`/`limit`
- 用 `HEAD~1` 当 git diff 的 BASE；整体审查用裸 `origin/main`
- 嵌套派发子代理（实现者 / 审查员再派子代理）
- 修复实现者不附带审查报告和原始任务上下文
- 整体审查失败不修复就继续 / 标记完成
- 用自审替代整体审查门控
- 在 main/master 上执行（未经用户明确同意）
- 忽略子代理提问；接受"差不多"的整体审查结果
