# 子代理驱动开发

派子代理执行计划。逐层并行执行实现，所有任务完成后进入整体双审查门控（整体 spec-review → 整体 code-review）。

## 前置条件

计划已被用户确认。未确认？停止。回去请用户审阅。

## 执行

```
读取计划 → 提取「执行分层」表 → TodoWrite 所有任务
  → 阶段 1：逐层并行执行（任务级零独立审查，实现即标记）
  → 阶段 2：整体双审查门控
```

不间断执行所有任务。只在以下情况停下：BLOCKED 无法解决、真正阻塞的歧义、全部完成。

## Controller 角色：纯协调者

| ❌ 不做 | ✅ 做 |
|--------|------|
| 读代码、审查代码 | 只读报告 |
| 修代码 | 只决定下一步 |
| 跳过整体任一审查 | 只协调层级推进 |
| 信任实现者报告未经验证 | 只在整体双审查通过后标记完成 |

## 阶段 0：分层编排

计划文档中的「执行分层」表已由 writing-plans 自动计算。Controller 只需要读取并执行。

> **分层由 writing-plans 计算，Controller 不重复分析依赖。** 如果分层表不存在或异常 → 退回 writing-plans 重新生成。

## 阶段 1：逐层并行执行（任务级零独立审查）

```
Layer 0 → 全部完成 → Layer 1（所有任务并行）→ 全部完成 → Layer 2 → ... → Layer N
```

**为什么任务级不派独立审查子代理？**

单任务 spec-reviewer 看不到完整需求地图 = 盲人摸象；单任务 code-reviewer 看到孤立 diff = 缺全局上下文易误报。**全局观来自整体审查，而非任务级重复审查**。任务级质量由以下机制兜底：

1. **契约约束**（硬约束）：实现者只能使用 Consumes 中声明的接口和类型
2. **强制 TDD**：实现者强制加载 TDD 技能，Red→Green→Refactor
3. **实现者四维自审**：完整性 / 质量 / 纪律 / 测试 → 报告 DONE_WITH_CONCERNS
4. **整体双审查兜底**：跨任务接口一致性、需求覆盖度、架构质量

### 同层并行规则

- 同层所有任务同时派发实现者子代理——互不等待
- 每个任务独立走：`实现(TDD) → 自审 → 提交 → 标记完成`
- 某任务失败：只影响该任务（派新实现者修复），同层其他任务继续
- 同层最慢的任务决定本层耗时

### 跨层串行规则

- 当前层所有任务完成后，才能进入下一层
- 上层未全部完成 → 禁止进入下层

### 为什么同层安全并行？

同层任务满足：修改不同文件 + Consumes 无相互引用 + 共享契约层类型。它们对着同一份接口写代码，互不干扰。

### Per Task 流程（任务级无独立审查）

```
派实现者（新子代理）
  → 强制加载 TDD 技能，Red→Green→Refactor
  → 实现者四维自审（完整性/质量/纪律/测试）
  → 报告：DONE | DONE_WITH_CONCERNS | BLOCKED | NEEDS_CONTEXT
  → Edit 计划文件 checkbox [- → x] → TodoWrite 标记完成
```

**详细 Prompt 模板：** `./implementer-prompt.md`

## 进度持久化（强制，任务级）

**每个任务完成后，立即回写计划文件——不是会话结束后批量更新，是每个任务完成即刻写入。**

### 执行时机

任务的实现+自审通过后（DONE / DONE_WITH_CONCERNS 处理后），**立即**执行持久化。

### 操作顺序

1. **先 Edit 计划文件：** 找到该任务的 checkbox，将 `- [ ]` 改为 `- [x]`
2. **再 TodoWrite 标记：** 在会话中更新任务状态为已完成

> **Edit 必须在 TodoWrite 之前。** 文件持久化优先于会话标记——即使会话中断，计划文件中的 checkbox 也反映真实进度。

### 失败处理

如果 Edit 失败（文件被锁定、权限问题等），**不要继续**。重试 Edit，最多 3 次。仍然失败 → 以 BLOCKED 状态暂停，向用户汇报。

### 为什么必须这样做？

- 会话 TodoWrite 只在当前会话有效——会话结束，进度丢失
- 计划文件是唯一的持久化真相源——中断后重开，Controller 能从 checkbox 状态恢复
- 实时回写确保任何时候看计划文件，都能知道哪些任务已完成、哪些还在进行

## 阶段 2：整体双审查门控

**所有任务完成后**，进入两道独立审查关卡。子代理看到完整需求地图和全部实现代码，**审查有全局观**。

```
整体 spec-review（需求覆盖度 + 任务间一致性）
  → ❌ → 派修复者 → 重新整体 spec-review（循环）
  → ✅
整体 code-review（代码质量 + 架构）
  → ❌ → 派修复者 → 重新整体 code-review（循环）
  → ✅
finishing-a-development-branch
```

### 整体 spec-review（第一关：需求合规）

1. Controller 派发**整体 spec-reviewer 子代理**，模板 `./spec-reviewer-prompt.md`
2. 提供：SPEC 路径 + Plan 路径 + 任务清单（Produces/Consumes/验收标准）+ 全部实现代码（git diff BASE..HEAD）
3. 子代理**按需读取全量代码**，自主定位功能实现完成度
4. 检查：需求覆盖度 / 任务间一致性 / 范围蔓延 / 需求曲解
5. ❌ 不通过：派**新实现者**修复（附整体审查报告 + 指派"修复 Task X 的 Y 问题"）→ 重新派发整体 spec-reviewer（循环直到通过）
6. ✅ 通过：进入整体 code-review

### 整体 code-review（第二关：代码质量）

1. Controller 调用 `Skill("superpowers:requesting-code-review")`
2. 技能加载后，按指引获取 BASE_SHA/HEAD_SHA，填 `code-reviewer.md` 模板，派发**整体 code-reviewer 子代理**
3. code-reviewer 看到**全量 diff**（BASE..HEAD），具备全局视角
4. 检查：架构 / 文件职责 / 可测试性 / 结构合规 / 测试质量 / 安全 / 性能
5. ❌ 不通过：派**新实现者**修复（附整体审查报告 + 指派"修复 Task X 的 Y 问题"）→ 重新调用 requesting-code-review（循环直到通过）
6. ✅ 通过：进入 finishing-a-development-branch

### 双审查的设计哲学

| 维度 | 整体 spec-review | 整体 code-review |
|------|-----------------|-----------------|
| 关注点 | 需求是否被实现 | 实现是否做得好 |
| 对照物 | SPEC 文档 + Plan 任务清单 | 代码 diff + 架构标准 |
| 典型发现 | 漏需求、需求曲解、范围蔓延、任务间接口不一致 | 架构问题、可测试性、文件膨胀、命名、错误处理、安全 |
| 修复方向 | 补功能、改接口语义 | 改实现、改结构 |

**两道关卡互补不重复**：spec-review 看"做了什么"，code-review 看"做得怎样"。

### 修复子代理授权

整体审查发现问题后，**派新实现者修复**：

- 派发时附带：**整体审查报告**（明确问题）+ **被指派 Task 编号**（"修复 Task X 的 Y 问题"）+ **原始任务描述**
- 修复子代理**新子代理**，不走老路
- 修复完成后**只重跑发现问题的那一道审查**（不重跑未发现问题的另一道），节省 token

## 派发铁律

| 角色 | 怎么派 |
|------|--------|
| 实现者 | 新子代理 |
| 实现者修复 | **新子代理**（附审查报告 + 指派 Task + 原始任务上下文） |
| 整体 spec-reviewer | **新子代理**（每次全新视角） |
| 整体 code-reviewer | **新子代理**（每次全新视角） |
| Controller | 只读报告、只决定下一步、只协调层级推进 |

## 并行派发规则

| 规则 | 说明 |
|------|------|
| 同层任务同时派发 | 所有同层任务在实现阶段同时启动，互不等待 |
| 任务级零独立审查 | 任务级不再派 spec-reviewer / code-reviewer |
| 任务失败不影响同层其他任务 | 失败的任务派修复子代理，其他任务继续 |
| 跨层必须串行 | 上层全部完成才能进入下层 |
| 整体双审查必须全通过 | 任一未通过 = 派修复者 + 重新该关卡 |
| 文件冲突已由分层表解决 | 分层表保证同层任务修改不同文件 |

## 绝对禁止

- 控制器自己读代码、自己审查
- 控制器自己修代码
- 任务级派独立 spec-reviewer / code-reviewer（已废除，整体审查覆盖）
- 跳过整体双审查任一关卡（spec-review 未通过就进 code-review）
- 整体 spec-review 失败不修复就直接进入整体 code-review
- 整体 code-review 失败不修复就标记完成
- 修复实现者不附带审查报告和原始任务上下文
- 跳过层级——上层未完成就进入下层
- 不同层的任务并行派发
- 只在 TodoWrite 标记完成但不回写计划文件 checkbox（进度必须持久化到文件）
- 整体双审查通过后，继续追加任务（破坏门控完整性）

## 处理实现者状态

| 状态 | 动作 |
|------|------|
| DONE | 标记完成（Edit checkbox → TodoWrite）|
| DONE_WITH_CONCERNS | 读顾虑。正确性/范围问题 → 修复后再标记。观察性意见 → 记录，正常标记完成 |
| NEEDS_CONTEXT | 补充上下文，重新派发 |
| BLOCKED | 上下文不足 → 补充后重派。需更强推理 → 升级模型。任务太大 → 拆分。计划问题 → 升级给用户 |

别忽略升级。别不改变就重试。卡住了就必须改变什么。

## 模型选择

- 使用能够胜任每个任务复杂度的最弱模型，以节省成本并提高速度。haiku（廉价） / sonnet（标准） / opus（最强）
- 快速审查任务（文档、风格、一致性） → 廉价模型。
- 机械任务（1-2 文件、清晰规格）→ 廉价模型。
- 集成任务（多文件、跨模块）→ 标准模型。
- 设计/架构 → 最强模型。
- 复杂审查任务（整体 code-review 的架构 / BUG 审查）→ 最强模型。
- 整体 spec-review（需求覆盖度审查）→ 标准模型（看代码找功能为主）。

## Prompt 模板

- `./implementer-prompt.md` — 实现者
- `./spec-reviewer-prompt.md` — **整体**规格合规审查员（按需读取全量代码）
- `skills/requesting-code-review/code-reviewer.md` — 整体代码质量审查员（通过 requesting-code-review 技能调用）

## 红线

- 别在 main/master 上执行
- 别跳过整体双审查任一关卡
- 别带未修复问题继续
- 别跨层并行——上层未完成，禁止进入下层
- 别在同层内串行——同层任务应同时派发，互不等待
- 别派任务级独立审查（已废除，整体审查覆盖）
- 别让子代理读计划文件（你提供完整文本）
- 别忽略子代理提问
- 别接受"差不多"的整体审查结果
- 别用自审替代整体双审查
- 控制器不审查、不修代码
- 别只标记 TodoWrite 不更新计划文件——进度必须持久化到文件，Edit 先于 TodoWrite
- 整体双审查通过后，别继续追加任务

子代理提问 → 清晰完整回答。整体审查发现问题 → 派修复子代理 → 重新该关卡 → 循环直到通过。任务失败 → 派修复子代理，别手动修。
