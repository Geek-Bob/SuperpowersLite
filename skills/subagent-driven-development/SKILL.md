# 子代理驱动开发

派子代理执行计划。每个任务：实现 → 合规审查 → 质量审查。通过后标记完成。

## 前置条件

计划已被用户确认。未确认？停止。回去请用户审阅。

## 执行

```
读取计划 → 提取「执行分层」表 → TodoWrite 所有任务 → 逐层并行执行
```

不间断执行所有任务。只在以下情况停下：BLOCKED 无法解决、真正阻塞的歧义、全部完成。

### 阶段 0：分层编排

计划文档中的「执行分层」表已由 writing-plans 自动计算。Controller 只需要读取并执行。

> **分层由 writing-plans 计算，Controller 不重复分析依赖。** 如果分层表不存在或异常 → 退回 writing-plans 重新生成。

### 阶段 1：逐层并行执行

```
Layer 0 → 全部通过 → Layer 1（所有任务并行）→ 全部通过 → Layer 2 → ... → Layer N
```

**同层并行规则：**

- 同层所有任务同时派发实现者子代理——互不等待
- 每个任务独立走完整流程：实现 → spec-review → code-review → 标记完成
- Task 1 在 code-review 时，Task 2 可能还在 spec-review——各自独立推进
- 某任务审查失败：只影响该任务（派新实现者修复 → 重新审查），同层其他任务继续
- 同层最慢的任务决定本层耗时

**跨层串行规则：**

- 当前层所有任务通过后，才能进入下一层
- 上层未全部通过 → 禁止进入下层

**为什么同层安全并行？**

同层任务满足：修改不同文件 + Consumes 无相互引用 + 共享契约层类型。它们对着同一份接口写代码，互不干扰。

## Per Task 流程（每个任务独立走）

```
派实现者 → TDD/测试/提交/自审
  → 派 spec-reviewer → 合规？
    → ❌ 派新实现者修复（附带原始上下文 + 审查问题清单）→ 重新审查
    → ✅ Controller 调用 requesting-code-review → 通过？
      → ❌ 派新实现者修复（附带原始上下文 + 审查问题清单）→ 重新审查
      → ✅ Edit 计划文件 checkbox [- → x] → TodoWrite 标记完成
```

## 进度持久化（强制）

**每个任务完成后，必须实时回写计划文件——不是会话结束后批量更新，是每个任务完成即刻写入。**

### 执行时机

任务的两阶段审查（spec-review + code-review）全部通过后，**立即**执行持久化。

### 操作顺序

1. **先 Edit 计划文件：** 找到该任务的 checkbox，将 `- [ ]` 改为 `- [x]`
2. **再 TodoWrite 标记：** 在会话中更新任务状态为已完成

> **Edit 必须在 TodoWrite 之前。** 文件持久化优先于会话标记——即使会话中断，计划文件中的 checkbox 也反映真实进度。

### 失败处理

如果 Edit 失败（文件被锁定、权限问题等），**不要继续**。重试 Edit，最多 3 次。仍然失败 → 以 BLOCKED 状态暂停，向用户汇报。

### 为什么必须这样做？

- 会话 TodoWrite 只在当前会话有效——会话结束，进度丢失
- 计划文件是唯一的持久化真相源——中断后重开，Controller 能从 checkbox 状态恢复
- 实时回写确保任何时候看计划文件，都能知道哪些任务已完成、哪些还在进行

## 两阶段审查

控制器只协调，不审查，不修代码。

### 第一阶段：规格合规

1. 派 spec-reviewer 子代理，模板 `./spec-reviewer-prompt.md`
2. 提供：完整任务内容 + 设计文档索引（路径 + 章节锚点，审查员按需对照原始规格验证）
3. ❌ → 派新实现者修复（附带原始任务上下文 + 审查员问题清单）→ 派新 spec-reviewer 重新审查
4. ✅ → 进入第二阶段

### 第二阶段：代码质量

1. Controller 调用 `Skill("superpowers:requesting-code-review")`
2. 技能加载后，按指引获取 BASE_SHA/HEAD_SHA，填 `code-reviewer.md` 模板，派子代理
3. ❌ → 派新实现者修复（附带原始任务上下文 + 审查员问题清单）→ 重新调用 requesting-code-review
4. ✅ → 标记完成

### 派发铁律

| 角色 | 怎么派 |
|------|--------|
| 实现者 | 新子代理 |
| 实现者修复 | **新子代理**（附带原始上下文 + 审查问题清单） |
| 审查员 | **每次新子代理**（全新视角，无偏见） |
| 控制器 | 只读报告、只决定下一步、只协调层级推进 |

### 并行派发规则

| 规则 | 说明 |
|------|------|
| 同层任务同时派发 | 所有同层任务在实现阶段同时启动，互不等待 |
| 同层内各任务独立推进 | 各自的 spec-review、code-review 独立走，不互相阻塞 |
| 任务失败不影响同层其他任务 | 失败的任务派修复子代理，其他任务继续 |
| 跨层必须串行 | 上层全部通过才能进入下层 |
| 文件冲突已由分层表解决 | 分层表保证同层任务修改不同文件 |

### 绝对禁止

- 控制器自己读代码、自己审查
- 控制器自己修代码
- 跳过任一审查
- 审查有未解决问题时进入下一任务
- 规格合规未通过就开始代码质量审查
- 修复实现者不附带原始上下文和审查问题清单
- 跳过层级——上层未通过就进入下层
- 不同层的任务并行派发
- 只在 TodoWrite 标记完成但不回写计划文件 checkbox（进度必须持久化到文件）

## 处理实现者状态

| 状态 | 动作 |
|------|------|
| DONE | 进入规格合规审查 |
| DONE_WITH_CONCERNS | 读顾虑。正确性/范围问题 → 修复后再审查。观察性意见 → 记录，继续审查 |
| NEEDS_CONTEXT | 补充上下文，重新派发 |
| BLOCKED | 上下文不足 → 补充后重派。需更强推理 → 升级模型。任务太大 → 拆分。计划问题 → 升级给用户 |

别忽略升级。别不改变就重试。卡住了就必须改变什么。

## 模型选择
- 使用能够胜任每个任务复杂度的最弱模型，以节省成本并提高速度。haiku（廉价） / sonnet（标准） / opus（最强） 
- 快速审查任务（文档、风格、一致性） → 廉价模型。
- 机械任务（1-2 文件、清晰规格）→ 廉价模型。
- 集成任务（多文件、跨模块）→ 标准模型。
- 设计/架构 → 最强模型。
- 复杂审查任务（代码BUG） → 最强模型。


## Prompt 模板

- `./implementer-prompt.md` — 实现者
- `./spec-reviewer-prompt.md` — 规格合规审查员
- `skills/requesting-code-review/code-reviewer.md` — 代码质量审查员（通过 requesting-code-review 技能调用）

## 红线

- 别在 main/master 上执行
- 别跳过审查
- 别带未修复问题继续
- 别跨层并行——上层未通过，禁止进入下层
- 别在同层内串行——同层任务应同时派发，互不等待
- 别让子代理读计划文件（你提供完整文本）
- 别忽略子代理提问
- 别接受"差不多"的规格合规
- 别用自审替代实际审查
- 控制器不审查、不修代码
- 别只标记 TodoWrite 不更新计划文件——进度必须持久化到文件，Edit 先于 TodoWrite

子代理提问 → 清晰完整回答。审查发现问题 → 修复 → 重新审查 → 循环直到通过。任务失败 → 派修复子代理，别手动修。
