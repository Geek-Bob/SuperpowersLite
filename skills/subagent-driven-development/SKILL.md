# 子代理驱动开发

派子代理执行计划。逐层并行实现。所有任务完成后过审查门控——需求侧 `spec-review` 永远跑，质量侧 `code-review` 仅当交付物含可执行代码时跑。

## 前置条件

计划已被用户确认。未确认？停止。

## 执行

```
读取计划 → 提取「执行分层」表 → TaskCreate 所有任务
  → 阶段 1：逐层并行执行
  → 阶段 2：审查门控（spec-review 必跑，code-review 按交付物分流）
```

不间断执行所有任务。只在以下情况停下：BLOCKED 无法解决、真正阻塞的歧义、全部完成。

## Controller 角色：纯协调者

| ❌ 不做 | ✅ 做 |
|--------|------|
| 读代码、审查代码 | 只读报告 |
| 修代码 | 只决定下一步 |
| 跳过必跑的 spec-review | 只协调层级推进 |
| 信任实现者报告未验证 | 只在审查门控通过后标记完成 |

## 阶段 0：分层编排

Controller 读取 writing-plans 已计算好的「执行分层」表，照表执行。**不重复分析依赖。**

分层表异常？退回 writing-plans 重新生成。

## 指针化派发

派发**只给指针，不给正文**。控制器在派发 prompt 里只放四样东西：

| 组件 | 内容 |
|------|------|
| 路径 | 计划文件绝对路径 + 目标文件路径 |
| 定位 | `offset` / `limit`（行号窗口），或精确章节标题 |
| 额外约束 | 本任务独有的边界（Auth Scope、禁改文件清单、专用规则） |
| 报告路径 | `.superpowers/sdd/<plan-slug>/task-N-report.md` |

**禁止写进派发 prompt：** 任务全文粘贴、会话历史回放、前序任务摘要、整份计划文件正文。

**为什么：** 有真实会话的派发 prompt 达 42k 字符，其中 99% 是粘贴的历史。规则管不住粘贴惯性——用行号指针让正文物理上不进上下文，而不是靠模型自觉。

### 行号解析约定

派发前**现场解析**任务行号，**不硬编码**：

```
grep -n "^### Task N:" <计划文件>
```

以该行号为起点、下一个 `### Task` 行为终点，据此填 `offset` / `limit`。N 精确匹配——`^### Task 1:` 不会误匹配 `### Task 10:`。

**防行号漂移：** 进度**只翻 checkbox（`- [ ]` → `- [x]`），不增删行**。新增或删除任何行都会让后续任务的 `offset` 失效，指针派发随之错位——这是「只翻 checkbox」的理由，不是格式洁癖。

### diff 获取协议（子代理自跑）

审查员与修复者**自跑 git diff**，控制器不代劳、不粘 diff：

1. `git diff --stat BASE..HEAD` → 先看全景（改了哪些文件、各多少行）
2. 按文件 `git diff -- <path>` → 分批精读（改动超 5 个文件时，先看 stat 概览再逐个读）

**BASE 禁令：** BASE 必须是派发前记录的 SHA。**禁止用 `HEAD~1`**——多 commit 任务会被静默丢弃前序 commit 的改动，审查员只看到最后一个 commit，漏审。**禁止**控制器把 diff 正文粘进任何 prompt。

### 产出路径约定

所有产出固定在仓库根的 `.superpowers/sdd/<plan-slug>/` 下：

- `task-N-report.md` — 实现者完整报告
- `review-N-report.md` — 审查员完整报告

**`plan-slug` 取法：** 计划文件名去扩展名。`docs/superpowers/plans/2026-09-23-foo.md` → `2026-09-23-foo`。

### 报告契约

详细内容**落 report 文件**，返回控制器的**只有四项**：状态 / commit / 一行测试摘要 / 顾虑。**禁止**把报告全文、测试日志、diff 正文贴回控制器。

### 禁止 ledger / progress.md

**只创建 report 类文件。** 进度持久化的唯一真相源是计划文件 checkbox（见「进度持久化」）。**禁止**创建 ledger、`progress.md`、逐任务历史记录——那是为应对上下文压缩的状态恢复机制，Lite 用计划文件 checkbox 已解决；再造一份只会制造第二个会不同步的真相源。

## 无开场白契约（实现者与审查员通用）

子代理返回控制器的每一行都必须携带信息。

- **第一行直接给结论**——不写"好的，我来分析一下""让我先看看代码"之类的开场白
- **每行 = 结论 / 带 `file:line` 的发现 / 跑过的检查**
- **禁止开场白、过程叙述、收尾总结**（"综上所述""希望这对你有帮助"）

**为什么：** 控制器只读报告。会话叙述、思考碎碎念、礼貌性总结对控制器是零信息、纯 token 浪费。

## 禁止嵌套派发

**实现者与审查员均不得再派子代理。** 控制器是所有派发的唯一入口。

- 实现者遇到无法完成的子问题 → 以 BLOCKED / NEEDS_CONTEXT 上报，由控制器决定下一步
- 审查员不得派"子审查员"分担审查

**为什么：** 嵌套派发会（1）制造重复审查席位——同一份代码被多个审查员从不同路径评估，结论互相矛盾；（2）让上下文树指数爆炸——每层子代理各持一份全量代码副本，token 成本失控。

## 阶段 1：逐层并行执行

```
Layer 0 → 全部完成 → Layer 1（所有任务并行）→ 全部完成 → Layer 2 → ... → Layer N
```

### 同层并行规则

- 同层所有任务同时派发——互不等待
- 每个任务独立走：`实现(TDD) → 自审 → 提交 → 标记完成`
- 任务失败：只影响该任务（派新实现者修复），同层其他任务继续
- 同层最慢任务决定本层耗时

### 跨层串行规则

- 当前层所有任务完成后，才能进入下一层
- 上层未全部完成 → 禁止进入下层

### 同层安全并行的前提

同层任务满足：修改不同文件 + Consumes 无相互引用 + 共享契约层类型。它们对着同一份接口写代码，互不干扰。

### 任务级质量兜底（零独立审查）

任务级不派独立审查子代理（**任务级零独立审查**）。质量由四重机制兜底：

1. **契约约束**：实现者只能使用 Consumes 中声明的接口和类型
2. **强制 TDD**：实现者强制加载 TDD 技能，Red→Green→Refactor
3. **实现者四维自审**：完整性 / 质量 / 纪律 / 测试 → 报告 DONE_WITH_CONCERNS
4. **整体审查门控**：spec-review 查跨任务接口一致性 + 需求覆盖度；交付物含可执行代码时追加 code-review 查架构质量

### Per Task 流程

```
grep -n "^### Task N:" <计划文件> → 得该任务 offset/limit
派实现者（新子代理，只传计划文件路径 + offset/limit + Consumes 契约 + 模块职责 + 报告路径）
  → 强制加载 TDD 技能，Red→Green→Refactor
  → 实现者四维自审（完整性/质量/纪律/测试）
  → 报告全文写入 task-N-report.md
  → 返回：状态 + commit + 一行测试摘要 + 顾虑（无开场白）
  → Edit 计划文件 checkbox [- → x] → TaskUpdate 标记完成
```

**详细 Prompt 模板：** `./implementer-prompt.md`

## 进度持久化（任务级强制）

**每个任务完成后立即回写计划文件。每个任务完成即刻写入，不是会话结束批量更新。**

### 执行时机

任务实现+自审通过后，**立即**执行持久化。

### 操作顺序

1. **派发时建档：** `TaskCreate({ subject, description, activeForm })` → 得 taskId
2. **任务开始时：** `TaskUpdate({ taskId, status: "in_progress" })`
3. **完成后先 Edit 计划文件：** 找到该任务的 checkbox，将 `- [ ]` 改为 `- [x]`
4. **再 TaskUpdate 标记：** `TaskUpdate({ taskId, status: "completed" })`

**Edit 必须在 TaskUpdate 之前。** 文件持久化优先于会话标记。

### 失败处理

Edit 失败？重试，最多 3 次。仍失败？以 BLOCKED 状态暂停，向用户汇报。

### 为什么

- TaskUpdate 的状态只在当前会话有效——会话结束，进度丢失
- 计划文件是唯一的持久化真相源——中断后重开，能从 checkbox 状态恢复
- 实时回写确保任何时候看计划文件，都知道哪些任务已完成、哪些还在进行

## 阶段 2：审查门控（按交付物分流）

**所有任务完成后**，进入审查门控。子代理看到完整需求地图和全部实现代码。

**分流规则：** 需求侧 `spec-review` **永远跑**；质量侧 `code-review` **仅当交付物含可执行代码时跑**，且**只审代码部分**。

```
整体 spec-review（需求覆盖度 + 任务间一致性）
  → ❌ → 派修复者 → 重新整体 spec-review（循环）
  → ✅
交付物含可执行代码？
  ├─ 否（纯文档 / 技能 Markdown）→ 跳过 code-review → finishing-a-development-branch
  └─ 是 → 整体 code-review（仅代码部分）
            → ❌ → 派修复者 → 重新整体 code-review（循环）
            → ✅ → finishing-a-development-branch
```

### 为什么纯文档 / 技能任务跳过 code-review

**这条理由必须保留**——否则后人会把 code-review 重新加回来。

code-review 的检查项是**错误处理、类型安全、Schema 迁移、安全隐患**。这些对技能 Markdown 是**无效项**：Markdown 没有控制流、没有类型、没有运行时、没有 schema。硬跑它只会产出「命名不够好」这类噪音 finding，并诱使修复者为了通过审查去改写文档措辞——偏离需求，纯亏 token。

需求侧审查对文档**完全有效**：漏需求、需求曲解、范围蔓延、任务间接口不一致，在文档里同样成立。所以纯文档 / 技能任务：**spec-review 跑，code-review 跳**。

### 例外：交付物含可执行代码（防一刀切）

技能 / 文档任务里夹带可执行代码（技能中内嵌 bash / node / python 片段，或附带的脚本）时：

- **code-review 只审那些代码片段**——按代码标准查错误处理、类型安全、安全隐患
- **文档部分仍走 spec-review**——不因为文件是 `.md` 就免审

**禁止**因为「这个任务主要是写文档」就整单跳过 code-review——那会把夹带的可执行代码放过去。

任务级仍然**零独立审查**——所有审查只在全部任务完成后整体进行（见「任务级质量兜底（零独立审查）」）。

### 整体 spec-review（需求侧：永远跑）

1. Controller 派发**整体 spec-reviewer 子代理**，模板 `./spec-reviewer-prompt.md`
2. 提供：SPEC 路径 + Plan 路径（子代理自读任务清单）+ BASE SHA（子代理自跑 git diff）+ 实现者报告路径
3. 子代理**按需读取全量代码**，自主定位功能实现完成度
4. 检查：需求覆盖度 / 任务间一致性 / 范围蔓延 / 需求曲解
5. ❌ 不通过：派新实现者修复（附整体审查报告 + 指派"修复 Task X 的 Y 问题"）→ 重新派发整体 spec-reviewer（循环直到通过）
6. ✅ 通过：交付物含可执行代码 → 进入整体 code-review（仅代码部分）；否则 → 直接进入 finishing-a-development-branch

### 整体 code-review（质量侧：仅当交付物含可执行代码时）

1. Controller 调用 `Skill("superpowers:requesting-code-review")`
2. 按指引获取 BASE_SHA/HEAD_SHA，填 `code-reviewer.md` 模板，派发**整体 code-reviewer 子代理**
3. code-reviewer 看到**全量 diff**（BASE..HEAD）
4. 检查：架构 / 文件职责 / 可测试性 / 结构合规 / 测试质量 / 安全 / 性能
5. ❌ 不通过：派新实现者修复（附整体审查报告 + 指派"修复 Task X 的 Y 问题"）→ 重新调用 requesting-code-review（循环直到通过）
6. ✅ 通过：进入 finishing-a-development-branch

### 两侧分工（不是「两道必跑关卡」）

| 维度 | 整体 spec-review | 整体 code-review |
|------|-----------------|-----------------|
| 何时跑 | **永远跑**（含纯文档 / 技能任务） | **仅当交付物含可执行代码** |
| 范围 | 全部交付物 | **仅可执行代码部分**（文档部分归 spec-review） |
| 关注点 | 需求是否被实现 | 实现是否做得好 |
| 对照物 | SPEC 文档 + Plan 任务清单 | 代码 diff + 架构标准 |
| 典型发现 | 漏需求、需求曲解、范围蔓延、任务间接口不一致 | 架构问题、可测试性、文件膨胀、命名、错误处理、安全 |
| 修复方向 | 补功能、改接口语义 | 改实现、改结构 |

**spec-review 看"做了什么"，code-review 看"做得怎样"。**

两道侧不是「都必须过」的关卡，而是**按交付物分流**：spec-review 覆盖全部交付物，code-review 只覆盖其中的可执行代码。判据是**交付物内容**，不是任务标签——标着「文档任务」却夹带 bash 的，照样要审那部分 bash。

### 修复子代理授权（ONE fix dispatch）

**一次审查暴露的全部 finding 打包给同一个修复者，一次派一个**——不按 finding 逐个派发。

派新实现者修复，附带：

- **整体审查报告**（列明全部 finding）
- **被指派 Task 编号**（"修复 Task X 的 Y 问题"）
- **原始任务描述**

**为什么 ONE：** 每个 finding 单独派一个修复者 → N 倍子代理启动成本 + N 份全量代码上下文重复加载；同一文件的多个 finding 还会互相覆盖。一次派一个，修完再重跑审查。

修复子代理走新子代理。修复完成后**只重跑发现问题的那一侧审查**，不重跑另一侧，节省 token。

## 派发铁律

| 角色 | 怎么派 |
|------|--------|
| 实现者 | 新子代理 |
| 实现者修复 | **新子代理**（附审查报告 + 指派 Task + 原始任务上下文） |
| 整体 spec-reviewer | **新子代理**（每次全新视角） |
| 整体 code-reviewer | **新子代理**（每次全新视角）——仅在交付物含可执行代码时派 |
| Controller | 只读报告、只决定下一步、只协调层级推进 |

## 并行派发规则

| 规则 | 说明 |
|------|------|
| 同层任务同时派发 | 所有同层任务在实现阶段同时启动，互不等待 |
| 任务失败不影响同层 | 失败任务派修复子代理，其他任务继续 |
| 跨层必须串行 | 上层全部完成才能进入下层 |
| 审查门控必须全通过 | spec-review 永远必跑；code-review 按交付物分流；任一未通过 = 派修复者 + 重新该侧 |
| 文件冲突已由分层表解决 | 分层表保证同层任务修改不同文件 |

## 绝对禁止

- 控制器自己读代码、自己审查
- 控制器自己修代码
- 跳过整体 spec-review（它永远必跑）
- 交付物含可执行代码却整单跳过整体 code-review
- 整体 spec-review 失败不修复直接进入整体 code-review
- 整体 code-review 失败不修复就标记完成
- 修复实现者不附带审查报告和原始任务上下文
- 跳过层级——上层未完成就进入下层
- 不同层的任务并行派发
- 只在 TaskUpdate 标记完成但不回写计划文件 checkbox
- 审查门控通过后，继续追加任务
- 创建 ledger / `progress.md` / 逐任务历史记录
- 把 diff 内容、报告全文或前序任务摘要粘进主上下文 / 派发 prompt
- 把任务全文、会话历史、整份计划文件正文粘进派发 prompt
- 用 `HEAD~1` 当 git diff 的 BASE
- 嵌套派发子代理（实现者 / 审查员再派子代理）

## 处理实现者状态

| 状态 | 动作 |
|------|------|
| DONE | 标记完成（Edit checkbox → TaskUpdate）|
| DONE_WITH_CONCERNS | 读顾虑。正确性/范围问题 → 修复后再标记。观察性意见 → 记录，正常标记完成 |
| NEEDS_CONTEXT | 补充上下文，重新派发 |
| BLOCKED | 上下文不足 → 补充后重派。需更强推理 → 升级模型。任务太大 → 拆分。计划问题 → 升级给用户 |

**别忽略升级。别不改变就重试。卡住了就必须改变什么。**

## Rulings（裁决记录）

计划是静态的，执行是动态的。现场偏离计划文本做判断时，记一行 Rulings，让用户能复核判断对错。

### 三个触发时机

| 触发 | 记什么 |
|------|--------|
| 审查发现与计划文本冲突 | 冲突点 + 裁决（改计划 / 改实现）+ 理由 |
| 实现者 BLOCKED 且控制器现场改计划 | 原计划文本 + 改成什么 + 为什么 |
| 整体审查不通过且裁决某 finding 不成立 | finding + 判不成立的理由 |

Rulings 的**格式契约由 writing-plans 计划模板定义**——本节只定义触发时机。

### 禁止

- 完整 Ledger
- `progress.md`
- 逐任务历史记录（每个任务做了什么）
- 决策之外的流水账（操作日志、命令回放）

只记「偏离计划文本的决策」，一行一条。没有决策 → 不记。

**收尾时：** Rulings 汇总进最终报告，供用户复核判断对错。

## 模型选择

- 用能胜任的最弱模型，省成本提速度。haiku（廉价）/ sonnet（标准）/ opus（最强）
- 快速审查（文档、风格、一致性）→ 廉价模型
- 机械任务（1-2 文件、清晰规格）→ 廉价模型
- 集成任务（多文件、跨模块）→ 标准模型
- 设计/架构 → 最强模型
- 整体 code-review（架构 / BUG 审查）→ 最强模型
- 整体 spec-review（需求覆盖度）→ 标准模型

### 轮次比 token 单价更重要

**最便宜的模型常常跑 2–3 倍轮次，总价反而更贵。** 便宜模型第一次没做对时会反复读文件、反复试错——每次重试都是一整轮完整上下文。选模型看**完成任务的期望总成本（单价 × 轮次）**，不看单价。

两类角色有**中档（sonnet）地板**，不得降到廉价模型：

- **审查员**——审查的产出是「判断」，判断失准的代价是漏审，比审查费贵得多
- **「从散文描述实现」的实现者**——计划不含实现代码，实现者要从验收契约反推实现，推理密度高于抄代码

只有机械任务（改文档措辞、翻转 checkbox、按清单逐条核对）才降到廉价模型。

### Prompt Caching：派发保持前缀稳定

派发子代理时**保持 prompt 前缀稳定**——固定的系统提示、固定的技能内容、固定的模板骨架放前缀，随任务变化的内容放后缀。命中缓存的输入按 **10%** 计费。前缀每变一次就丢一次缓存命中，所以别为了「更漂亮」重排 prompt 结构。

## Prompt 模板

- `./implementer-prompt.md` — 实现者
- `./spec-reviewer-prompt.md` — 整体规格审查员（按需读取全量代码）
- `skills/requesting-code-review/code-reviewer.md` — 整体代码审查员（通过 requesting-code-review 技能调用）

## 红线

- 别在 main/master 上执行
- 别跳过整体 spec-review（它永远必跑）
- 别整单跳过整体 code-review——交付物含可执行代码时必须审，且只审代码部分
- 别带未修复问题继续
- 别跨层并行——上层未完成，禁止进入下层
- 别在同层内串行——同层任务应同时派发，互不等待
- 别让子代理读整个计划文件——只给它任务章节的 `offset`/`limit`
- 别把前序任务摘要 / 会话历史 / 整个计划文件正文写进派发 prompt
- 别把 diff 内容粘进派发 prompt——让子代理自跑 `git diff`
- 别用 `HEAD~1` 当 BASE
- 别嵌套派发子代理
- 别创建 ledger / `progress.md` / 逐任务历史记录
- 别忽略子代理提问
- 别接受"差不多"的整体审查结果
- 别用自审替代整体审查门控
- 控制器不审查、不修代码
- 别只标记 TaskUpdate 不更新计划文件——进度必须持久化到文件，Edit 先于 TaskUpdate
- 审查门控通过后，别继续追加任务

**子代理提问 → 清晰完整回答。整体审查发现问题 → 派修复子代理 → 重新该侧审查 → 循环直到通过。任务失败 → 派修复子代理，别手动修。**
