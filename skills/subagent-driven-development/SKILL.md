# 子代理驱动开发

派子代理执行计划，逐层并行；所有任务完成后过审查门控——需求侧 `spec-review` 永远跑，质量侧 `code-review` 仅当交付物含可执行代码时跑。

**前提：任务基本独立。** 紧耦合任务不适用本技能（executing-plans 同样不适用）——手工执行，或回头 brainstorming。与 Native 内联的完整对比与选择判据见 writing-plans 执行交接节。

## Setup

1. 计划已获用户确认——未确认，停止。
2. 用 `superpowers:using-git-worktrees` 创建或校验隔离工作区。**未经用户明确同意，绝不在 main/master 上开始实现。**
3. 通读计划，记下 Global Constraints，逐任务建 todo；计划点名了 Spec 就也读它——计划内部冲突对照 spec 裁决。读不到 spec 在最终报告记一句，据之所做裁决标为临时。
4. `git rev-parse HEAD` 记录 Base SHA——每任务派发与整体审查的 BASE 都用它。
5. 第 1 个任务前加载 `superpowers:test-driven-development`，它管辖每个任务的每一步；计划写着「先写失败测试」不构成豁免。

## 控制器纪律

| ❌ 不做 | ✅ 做 |
|--------|------|
| 读代码、审查代码、修代码 | 只读报告、只决定下一步、只协调层级推进 |
| 信任实现者报告未验证 | 只在审查门控通过后标记完成 |

**只有四类事能让你停下**：不可逆或破坏性操作、安全敏感动作、worktree 之外的副作用（merge、push 共享分支、发布）、计划烂到每条前路都是猜。终态——BLOCKED 无法解决、真正阻塞的歧义、全部完成——同样停下。其余一律现场裁决（记 Ruling）继续。

## 每个任务

照 writing-plans 已算好的「执行分层」表执行——不重复分析依赖；分层表异常退回 writing-plans 重新生成。

### 派发

派发 prompt 由五样东西构成，别的都不进：

| 组件 | 内容 |
|------|------|
| 路径 | 计划文件绝对路径 + 目标文件路径 |
| 定位 | `offset` / `limit`（行号窗口），或精确章节标题 |
| 额外约束 | 本任务独有边界（Auth Scope、禁改文件清单、专用规则） |
| 相关 Ruling | `## Rulings` 区涉及本任务 Consumes / 文件的历史裁决，没有则省略——Rulings 在计划头部、不在任务窗口内，实现者自己看不到 |
| 报告路径 | `.superpowers/sdd/<plan-slug>/task-N-report.md` |

**行号现场解析，不硬编码：** `grep -n "^### Task N:" <计划文件>`，以该行为起点、下一个 `### Task` 行为终点（N 精确匹配，`^### Task 1:` 不会误匹配 `### Task 10:`）。计划含代码围栏时先确认命中行不在围栏内——任务正文出现 `### Task N:` 字样（示例代码、模板片段）时裸 grep 算出错误窗口，实现者照错窗口干活，**静默错任务**。

**进度只翻 checkbox（`- [ ]` → `- [x]`），不增删行**——任何增删都让后续任务的 offset 失效。由此，现场改计划触发「在飞保护」：同层还有任务没返回时推迟到层结束；等不及（阻塞的就是本层），改完立即按新行号重派受影响任务。

**模型分档**（派发 prompt 的模型字段永远显式——不写就继承你当前会话的模型，分档被静默击穿）：

- 机械任务（1-2 文件、清晰规格；改文档措辞、翻 checkbox、按清单核对）→ 廉价（haiku）
- 集成任务（多文件跨模块）→ 标准模型（sonnet）
- 设计/架构、整体 code-review → 最强模型（opus）
- 小型修复 diff 的局部 re-review → 廉价-中档（审查类的唯一例外）

**中档地板**：审查员与「从散文描述实现」的实现者不得降到廉价模型——前者产出是判断，后者要从验收契约反推实现；最便宜的模型常跑 2–3 倍轮次，按期望总成本（单价 × 轮次）选，不按单价。派发保持前缀稳定（固定内容在前、任务变化内容在后），命中 Prompt Caching 的输入按 10% 计费。

**同形小任务合并派发**：同层多个同类小改（一行修改、常量替换、加字段）合成一份简报整批发给一个子代理、diff 当整体审——每次派发都重付数十 k 固定开销，同形小任务最付不起。

**同层并行、跨层串行**：同层所有任务同时派发、互不等待；失败任务派新实现者修复，其余继续；当前层全部完成才进下一层。并行前提由分层表保证（修改不同文件 + Consumes 无相互引用 + 共享契约层类型）。**git 暂存区是共享资源**——实现者只 add 本任务文件，commit 用路径限定（`git commit -m "<msg>" -- <本任务文件>`），撞 `index.lock` 等 2 秒重试：撞锁只是报错，并发暂存把别人 add 一半的文件裹进自己的 commit 才是静默灾难。

**禁止嵌套派发**：实现者与审查员均不得再派子代理——阻塞以 BLOCKED / NEEDS_CONTEXT 上报，控制器是所有派发的唯一入口。

### 报告与进度

**任务级只有任务自审**（完整性 / 质量 / 纪律 / 测试，有顾虑报 `DONE_WITH_CONCERNS`）——实现者只看得到自己那段 offset/limit，查不了跨任务一致性，这正是末尾审查门控存在的理由。

**输出契约**：报告全文落 `.superpowers/sdd/<plan-slug>/task-N-report.md`（审查员落 `review-N-report.md`），返回控制器只有四项——状态 / commit / 一行测试摘要 / 顾虑。**顾虑带类型标签**：`[bug]` 未修的已知问题 / `[观察]` 不阻塞的疑虑 / `[下一步]` 建议后续；`[bug]` 不当观察混过——要么修完再报 DONE，要么进最终报告「未解 bug」清单。第一行直接给结论，无开场白、无过程叙述、无收尾总结；测试日志与 diff 正文不贴回控制器。

| 状态 | 动作 |
|------|------|
| DONE | Edit checkbox → TaskUpdate |
| DONE_WITH_CONCERNS | `[bug]`/正确性问题 → 修复后再标记；`[观察]` → 记录，正常标记；`[下一步]` → 进最终报告 |
| NEEDS_CONTEXT | 补充上下文，重新派发 |
| BLOCKED | 上下文不足→补充重派；需更强推理→升级模型；任务太大→拆分；计划问题→升级用户 |

**别不改变就重试。卡住了就必须改变什么。**

任务完成**立即**回写：先 Edit 计划文件 checkbox，**再** TaskUpdate——文件是唯一持久化真相源，TaskUpdate 只在当前会话有效。Edit 失败重试 3 次，仍失败按 BLOCKED 上报。

**产出隔离**：产出固定在仓库根 `.superpowers/sdd/<plan-slug>/`（`plan-slug` = 计划文件名去扩展名），并建 `.superpowers/sdd/.gitignore`（一行 `*`）使其不进 `git status`、不被 `git add` 带走。**禁止** ledger / `progress.md` / 逐任务历史——checkbox 已是唯一真相源，再造一份只会制造第二个会不同步的真相源。`git clean -fdx` 会连报告一起删，但审查不依赖报告（审查员自跑 diff），缺失时照常派发。

**中断恢复**（上下文压缩 / 会话重开后）：已 `[x]` 的任务不重派，从首个未勾任务续跑；续跑前 `git status` + `git log --oneline -5` 查半成品（未提交改动或半截 commit），续用或回滚，记一条 Ruling 再派发。**信计划文件与 git log，不信会话记忆。**

## 审查门控（所有任务完成后）

**分流**：`spec-review`（需求覆盖度 / 任务间一致性 / 范围蔓延 / 需求曲解）**永远跑**；`code-review`（架构 / 文件职责 / 可测试性 / 结构合规 / 测试质量 / 安全 / 性能）**仅当交付物含可执行代码时跑、只审代码部分**。判据是交付物内容，不是任务标签：纯文档 / 技能任务跳过 code-review（裁决理由见 UPSTREAM.md「Lite 独有」）；夹带内嵌 bash / node / python 片段的，只审那些片段（错误处理 / 类型安全 / 安全隐患），文档部分归 spec-review。**spec-review 看"做了什么"，code-review 看"做得怎样"。**

1. **完整审查只跑这一轮**：派 spec-reviewer 子代理（新子代理），模板 `./spec-reviewer-prompt.md`（SPEC 路径 + Plan 路径 + BASE SHA，自跑 git diff）；交付物含可执行代码时再调 `Skill("superpowers:requesting-code-review")` 派整体 code-reviewer，看全量 diff（BASE..HEAD）。两份 finding 汇成一张清单。
2. **ONE fix**：全部 finding 打包给**同一个**新实现者，一次派一个（N 个 finding 单独派 = N 倍启动成本 + N 份全量代码重复加载，同文件 finding 还互相覆盖），附整体审查报告 + 指派「修复 Task X 的 Y 问题」+ 原始任务描述。
3. **逐条核对，不重审**：拿修复后的 diff 对每条 finding 给出处置——**已修**（附 `file:line`）/ **判不成立**（记 Ruling）/ **延后**（进最终报告）。核对不产生新 finding。
4. **核对通过 →** `finishing-a-development-branch`。门控通过后不追加任务。

**核对的输出形状是核对表，不是新报告：**

| 原 finding | 处置 | 证据 |
|---|---|---|
| [finding] | 已修 / 判不成立 / 延后 | `file:line` 或 Ruling 引用 |

外加一个受限槽位：**新引入缺陷**——仅限本次修复 diff 引入、必须指认 `file:line`；没有就写「无」。

**只有新引入缺陷能开第二轮**：修复前 SHA 记为 `FIX_BASE`，只审 `FIX_BASE..HEAD`，修完再核对一次。**上限 2 轮**——仍有残余，全量上呈用户，含「为什么修不掉」。

**结论冲突不是新 finding。** 后一轮结论推翻已采纳的裁决（"上一轮判 X 是缺陷，我据此改了；这一轮说 X 不是"）→ **不得自动改**，写进最终报告「结论冲突清单」：第 N 轮判什么、第 M 轮判什么、我按哪轮动了手、现在停在哪，交用户裁决。**来回改反比漏检更贵**——漏检留一处缺陷，改反留下错误实现加一份说不清的 git 历史。

**BASE 三禁令**（审查员与修复者自跑 diff，控制器不代取、不粘 diff 正文进任何 prompt）：

- BASE 用派发前记录的 SHA；整体审查用 `git merge-base origin/main HEAD`。**禁用 `HEAD~1`**（多 commit 任务丢前序 commit，静默漏审）、**禁用裸 `origin/main`**（main 前进后新文件显示成幻影删除）
- 审查前确认 BASE 是 HEAD 的**祖先**且 `BASE..HEAD` 非空——否则实现者可能提交到了别的分支，审查员对空 range 给出「干净」结论放行；不满足按 BLOCKED 上报
- 先 `git diff --stat BASE..HEAD` 看全景，再按文件 `git diff -- <path>` 精读（改动超 5 个文件先看 stat 概览）

**控制器不得预判 finding**：派发 prompt 出现「不要标记 X」「X 不算缺陷」「最多 Minor」「这个计划就是这么选的」——你正在替审查员做决定；误报让它报出来，在核对阶段裁定。**审查员只读、不接受辩解**——跑 `git checkout` 会让后续 commit 变成孤儿；实现者的「我故意不抽象」不是证据，代码才是。**「无法从 diff 判定」是有效结论**：审查员继续审其余部分，这些条目由控制器逐条裁定（控制器持有计划与跨任务上下文，审查员没有）；确认真缺口进 ONE fix。

**Minor 分流**：审查员标 Minor 的不进修复流程，但**先按效果重判**——标签评的是 spec 的沉默，不是用户实际拿到什么；够格的升进修复。其余逐条记进最终报告「延后的 Minor」清单（穷尽列举），finishing 时交用户裁决。每条 Minor 要么被修、要么被显式延后并告知用户，没有第三种归宿。

## Rulings 与收尾

现场偏离计划文本时记一行 Ruling（格式契约由 writing-plans 计划模板定义），触发时机三个：

| 触发 | 记什么 |
|------|--------|
| 审查发现与计划文本冲突 | 冲突点 + 裁决（改计划 / 改实现）+ 理由 |
| 实现者 BLOCKED 且控制器现场改计划 | 原计划文本 + 改成什么 + 为什么 |
| 整体审查不通过且裁决某 finding 不成立 | finding + 判不成立的理由 |

只记偏离计划的决策，一行一条；没有决策不记。**收尾时** Rulings 汇总进最终报告供用户复核；code-reviewer「Declined to judge」清单一并逐条裁决（接受/不接受 + 理由）——模板向审查员承诺过搁置不会被静默丢弃，控制器是兑现人。**结论冲突清单**（见审查门控）同样穷尽列出。

## 常见合理化

| 借口 | 现实 |
|------|------|
| "我自己读 diff 审一遍更快" | 你是协调者——inline 审 diff 烧掉驱动工作所需的上下文；只有 finding 该回到你这里 |
| "把前序任务摘要粘进派发，帮它省事" | 真实会话的派发达 42k 字符、99% 是粘贴历史；行号指针让正文物理上不进上下文 |
| "改动很简单，我顺手修了" | 控制器修代码跳过了审查门控；简单改动也走派发 |
| "实现者解释了原因，撤掉这条 finding" | 理由不是证据，代码才是；finding 只在核对阶段裁定 |
| "复审又出了新 finding，那就再修一轮" | 新 diff 是新审查面，重审结构上没有终点——核对只认「本次修复引入、指认得出 `file:line` 的」缺陷 |
| "这轮说上轮判错了，我改回去" | 结论冲突上呈用户，不自动改反——来回改反比漏检更贵 |
| "修复很小，跳过核对" | 未核对的修复是回归的入口；逐条核对比重审便宜得多 |
| "差不多就放行吧" | 审查员的 Minor 会进「延后的 Minor」清单交用户，不需要你放水 |
| "审查通过后顺手再补一个任务" | 门控通过即收尾；追加任务回 writing-plans 走新轮 |
