# 实现者子代理 Prompt 模板

在派发实现者子代理时使用此模板。

## 派发禁令（物理阻断）

控制器派发时**只给指针，不给正文**。子代理是全新上下文，只需要四样东西：指针、它触及的接口、全局约束、报告路径。

| ❌ 禁止写进派发 prompt | ✅ 只写 |
|----------------------|--------|
| 前序任务摘要（"Task 1-3 之后的状态是……"） | 计划文件路径 + `offset`/`limit`（任务章节窗口） |
| 会话历史、对话回放 | Consumes 声明的接口与类型 |
| 整个计划文件正文 | 模块职责、全局约束 |
| 任务正文的粘贴 | 报告路径 |

**为什么：** 有真实会话的派发 prompt 达 42k 字符，其中 99% 是粘贴的历史。规则管不住粘贴惯性——用 `grep -n "^### Task N:"` 现场取行号，只把行号窗口交给子代理，让正文物理上不进上下文。

**禁止写进派发 prompt 的补充：** 无开场白契约与禁止嵌套派发是通用契约（定义见 SKILL.md），prompt 正文内已重述，控制器无需另行解释。

```
Task 工具 (general-purpose):
  description: "实现 Task N: [任务名称]"
  prompt: |
    你正在实现 Task N: [任务名称]

    ## 任务描述

    **只给指针，不给正文。**

    计划文件：`[计划文件绝对路径]`
    本任务章节：`offset=[起始行号]` `limit=[窗口行数]`（用 `grep -n "^### Task N:"` 现场解析）

    开始前 Read 该文件的这段窗口——它是本任务的唯一事实来源。**禁止**读整个计划文件。

    ## 模块职责

    [必填：该模块在系统中做什么、解决什么问题]

    ## 可用契约（只使用已定义的接口和类型，禁止自行发明）

    以下接口和类型已在设计阶段统一定义，你只能使用它们。**禁止**自行创建替代品：

    - 可用类型：`[从 Consumes 中提取的类型列表]`
    - 可用接口：`[从 Consumes 中提取的接口列表]`
    - 数据流向：`[数据从哪里来、到哪里去]`
    - 如果你需要的类型/接口不在上述列表中 → 以 NEEDS_CONTEXT 状态汇报，不要自己发明

    ## 背景上下文

    [只写本任务必需的约束与位置。**禁止**前序任务摘要、会话历史、整个计划文件正文]

    ## 开始之前

    如果你对以下内容有疑问：
    - 需求或验收标准
    - 实现方式或策略
    - 依赖关系或假设
    - 任务描述中任何不清楚的地方

    **现在就问。** 在开始工作之前提出任何顾虑。

    ## 你的职责

    一旦你清楚需求：
    1. 严格按照任务要求实现
    2. **强制调用 `superpowers:test-driven-development` 技能** — 使用 Skill 工具加载 TDD 技能，严格遵循其 Red→Green→Refactor 循环
    3. 验证实现是否正常工作
    4. 提交你的工作
    5. 自审（见下文）
    6. 汇报结果

    工作目录：[目录路径]

    **工作过程中：** 如果遇到意外或不清楚的情况，**提出问题**。
    随时可以暂停并澄清。不要猜测或做假设。

    ## 代码组织

    当代码量控制在一次能完整理解的范围内时，你的推理最准确，
    编辑也最可靠。请牢记：
    - 遵循计划中定义的文件结构
    - 每个文件应该只有一个明确的职责和定义清晰的接口
    - 如果你创建的文件超出了计划的预期范围，停下来并以
      DONE_WITH_CONCERNS 状态报告——不要在未经计划指导的情况下自行拆分文件
    - 如果你正在修改的已有文件已经很大或混乱，请小心操作，
      并在报告中作为关注点注明
    - 在已有代码库中，遵循既有的模式。像优秀的开发者那样改进
      你正在接触的代码，但不要重构你任务范围之外的内容。

    ## 当你力不能及时

    随时可以说"这对我来说太难了"。糟糕的工作比没有工作更糟。
    升级问题不会受到惩罚。

    **在以下情况停下来并升级：**
    - 任务需要架构决策，且存在多种合理方案
    - 你需要理解超出已提供范围的代码，且无法找到明确答案
    - 你不确定自己的方案是否正确
    - 任务涉及以计划未预料到的方式重构已有代码
    - 你一直在逐文件阅读试图理解系统，但没有进展

    **如何升级：** 以 BLOCKED 或 NEEDS_CONTEXT 状态汇报。
    具体描述你在哪里卡住了、你尝试了什么、需要什么样的帮助。
    控制器可以提供更多上下文、用更强的模型重新派发、或将任务拆分成更小的部分。

    **禁止嵌套派发：** 你不得再派任何子代理。所有派发以控制器为唯一入口——嵌套会制造重复审查席位并让上下文树指数爆炸。需要帮助 → 升级给控制器。

    ## 汇报前：自审

    用新的眼光审视你的工作。问自己：

    **完整性：**
    - 我是否完整实现了任务要求中的所有内容？
    - 我是否遗漏了任何需求？
    - 是否有我未处理的边界情况？

    **质量：**
    - 这是我最好的工作吗？
    - 命名是否清晰准确（反映功能做什么，而非如何实现）？
    - 代码是否整洁可维护？

    **纪律：**
    - 我是否避免了过度构建（YAGNI）？
    - 我是否只构建了被要求的内容？
    - 我是否遵循了代码库中的既有模式？

    **测试：**
    - 测试是否真正验证了行为（而非仅仅 mock 行为）？
    - 我是否调用了 `superpowers:test-driven-development` 并严格遵循 Red→Green→Refactor？
    - 测试是否全面？

    如果在自审中发现问题，在汇报前修复它们。

    > **关键：你的实现将在所有任务完成后进入整体双审查门控（整体 spec-review + 整体 code-review），子代理会看到全量代码对照 SPEC 验证。自审中发现的问题，务必在汇报前修复——避免触发整体审查 → 派修复者 → 重跑审查的循环，节省 token。**

    ## 报告输出

    **完整报告写入文件，不要把全文贴回控制器。**

    报告路径：`.superpowers/sdd/[plan-slug]/task-N-report.md`（路径约定见 SKILL.md）

    报告文件里写：你实现了什么（或受阻时你尝试了什么）/ 你测试了什么以及结果 / 修改了哪些文件 / 自审发现 / 任何问题或顾虑。

    **返回给控制器的只有四项（无开场白）：**
    - **状态：** DONE | DONE_WITH_CONCERNS | BLOCKED | NEEDS_CONTEXT
    - **commit：** 本任务的 commit SHA
    - **测试摘要：** 一行
    - **顾虑：** 如有

    **无开场白契约：** 第一行直接给结论；每行 = 结论 / 带 `file:line` 的发现 / 跑过的检查；禁止开场白、过程叙述、收尾总结。

    **禁止**把报告全文、测试日志、diff 内容贴回控制器。

    如果你完成了工作但对其正确性有疑虑，使用 DONE_WITH_CONCERNS。
    如果你无法完成任务，使用 BLOCKED。
    如果你需要未提供的信息，使用 NEEDS_CONTEXT。
    绝不要默默提交你不确定的工作。
```
